# worker

`Bun.cron` jobs registered in `src/index.ts` (`job/`), plus one-off maintenance scripts in `src/script/`. Scripts run against the production `.env`, and only some are dry runs by default (`APPLY=1` to write), so read a script before running it. Pure logic goes in `src/lib/` beside its test (`serial-math.ts` is the model).

From `@repo/api`, import only modules whose import chain stays clear of `env.ts`. `env.ts` validates the web app's whole `serverEnv` (Discord, S3, SES and more) as it loads, and the worker container has none of those, so the worker dies on start. `services/redis` imports it, and so does every module that imports `services/redis`, such as `services/market/currency-rates`. Before importing an `@repo/api` service, follow its imports. Read such tables directly with `db`, as `update-currency-rates` and `snapshot-price-history` do. `src/import-boundary.test.ts` fails when the bundle reaches `env.ts` or `services/redis`.

## One run at a time

Register every cron job through `safeRun(tag, job)` in `src/index.ts`, with the job's kebab-case log tag: it runs the job under the Valkey lock `worker:lock:<tag>`, so a second worker, or a slow run overlapping its next tick, skips. A shutdown frees the locks of jobs still running. The trade verifier takes its own lock and passes `{ lock: false }`. A long-lived subscription that must run on one worker only goes through `whileLeader` (`src/lib/redis-lock.ts`), as the activity relay does.

## Logging

Jobs log only through `log(tag)` (`src/lib/log.ts`). A run that changed something logs one `info` summary; a run that changed nothing stays silent. Per-item lines go to `debug`, shown only with `WORKER_LOG_LEVEL=debug`. A job running every few minutes adds its counts to a `heartbeat`, which logs one line an hour. Drift and failures that retry on their own are `warn`, one line per run with a count; a failed job, or a failure only a person can fix (an expired Cosmo refresh token), is `error`. `src/script/` prints to the console, since its output is the point.

## Held transfers

`job/collection.ts` (tag `fix-collection`, every 5 minutes and on startup) replays the indexer's `pending_transfer` rows once Cosmo returns a token's metadata: it creates the collection if new, the objekt, its transfers and the outbox rows for non-mints, applies and stamps the token's unapplied `transferability_update` rows, and deletes the held rows, in one transaction per token (`lib/pending-replay.ts` plans it). Transferability follows the same finality rule: the replay applies only final `transferability_update` rows, and each run then settles the rows left unapplied on objekts that exist, never over a newer applied change and never for a token with a change still in a hot block. Only tokens whose every held row is at or below `squid_processor.status` height replay: a hot block can still be reorged out, and the worker's write would survive it. The verifier's `seenUntil` stops one second before the oldest held transfer (`trade-verifier/indexer-head.ts`), so a held send never lets a deadline pass; that is why the replay runs every 5 minutes, since until it does every running trade and the staff console read the indexer as behind.

## Offline serials

Serials of objekts minted offline come from `populateSerialOffline` (`job/populate-serial.ts`), checked every 15 minutes and weekly by `job/verify-batch-boundaries.ts`. The model:

- Modhaus reserves token-id ranges per **batch**. A collection has many non-contiguous batches; the serial runs continuously across them, and an unminted token inside a reserved range still consumes a serial.
- From Atom02 on, batches are whole **100-token blocks** separated by one to three foreign tokens. Earlier seasons are listed in `preBlockSeasons` (`@repo/lib/serial`, which the API's printed estimate also reads); Atom01 is scattered and outside the model.
- Discovery only sees minted tokens, so `refineBatches` (`job/serial-batches.ts`) fills reserved gaps and snaps lengths to whole blocks. Gap tokens come from the indexer database, not the Cosmo API. The indexer lacks a token id Cosmo assigned to another collection but never minted on chain (in Atom02 301A, unclaimed Divine01/Ever01 Z copies reserved between batches: no Transfer log on chain, checked 2026-11-08), so rediscovery keeps the Cosmo API: an indexer-only rerun gave the same serials for Cream02 but merged Atom02 batches across such tokens. `refineBatches` also takes `knownForeign` separators; the verifier passes the foreign edge tokens it learned (from the indexer or its probes) and `discoveryBoundaries` of the rediscovered batches.
- v1 serials are ground truth: an objekt minted before `V1_CUTOFF_MS` anchors its batch exactly. Batches with no such anchor (all of Summer26) are estimates.
- `objektNo` from the authenticated Cosmo API is visible only to the objekt's owner, so it is no general source of truth.
- Manual anchors are ground truth like v1 serials: reported `(tokenId, serial)` pairs in `collection.serial_anchors` that pin the batch their token sits in (v1 wins on the same token). Every serial write must pass them, and `computeOfflineSerials` / `computeOfflineSerialUpdates` take them as a required argument so a missed caller fails to type-check; only the holdout measurements in `refine-serial-batches.ts` and `script/drop-grid.ts` pass `[]`, on purpose.
- Add, remove or list anchors with `script/serial-anchor.ts`; `add` and `remove` are a dry run until `APPLY=1`.
- An "A" drop of a block season gives each member an equal **slot** in member order, with foreign minted tokens skipped as separators. Discovery cannot see where a member with few mints starts, so `fitDropGrid` (`lib/drop-grid.ts`) fits the slot size from the whole drop. A drop is **grid-fitted** only when exactly one size fits: every member token lands in its own slot, every member has a mint in its slot, and the token after the drop's end is foreign. Slots need not be whole hundreds (Binary02 304A uses 180). `applyGrids` (`job/serial-batches.ts`) puts the slot in place of the member's batches inside the drop and runs after `refineBatches` on every path that stores ranges, so a rediscovery never undoes it. Anchors still pin the batch they sit in, so they outrank the grid. Ambiguous and unfitted drops keep their discovered ranges. The verifier fits each drop once per run and skips the Cosmo edge probes for batches inside a grid-fitted drop, since foreign tokens already confirm those edges. Its indexer check for a foreign mint inside a stored range still covers them.
- The verifier makes two passes under the `serial-offline` lock, both off populate's 5-minute grid and neither calling the Cosmo API except to rediscover a drifted collection. Every 15 minutes (:02, :17, :32, :47), `verifyRecentDrift` matches the last 24 hours of mints against every stored range in memory (`driftCandidates`, `lib/drift-candidates.ts`; a SQL join took 98 s) and gives only the collections whose range holds another collection's mint the checks below. The window covers mint times because the held-transfer replay inserts objekts late with their original mint time. A mint with no collection yet is skipped, since the checks ignore it. A range too narrow shows as a _new_ own mint outside it, which populate rediscovers; an already-numbered own token outside the ranges waits for the weekly pass. A candidate whose rediscovery gives back the same ranges is skipped for 24 hours while all its foreign tokens are ones already tried (`stuck`, per process), so it doesn't call Cosmo on every pass. A candidate whose check throws counts as failed without stopping the rest, and the passes report through an hourly `heartbeat`. A skipped pass logs a `warn` (`safeRun`'s `warnOnSkip`): populate outlasting a pass during a busy drop is when drift matters most. Weekly at Sunday 19:08 UTC (Monday 03:08 in Malaysia, outside the 15-minute minutes so the two never race for the lock), `verifyBatchBoundaries` checks every collection, as a backstop; it holds the lock about 10 minutes, and a pass skipped or failed at 19:08 runs again at 19:38. Every check skips collections whose every batch holds a v1 objekt, checks the indexer for a foreign mint inside an unanchored range and judges each batch's edge tokens by their indexer owner. Probing the edge tokens the indexer lacks through the Cosmo API is manual only (`PROBES=recent|all`, default `none`): a dry run on 2026-11-08 made 14,465 calls over the last 8 weeks' collections and found nothing the indexer missed. A manual run takes `PROBES` beside `DRY_RUN=1`, or `RECENT=1` for the 15-minute pass.
- Some drops are reserved member by member: one member's A collections of a season sit back to back in equal slots (Cream02 334A–337A, 304A–307A), which `loadDrop` never fits since it pools a whole collection number. A **member run** is such a set, split wherever another A collection minted between two of them or they lie over 5000 tokens apart (`loadMemberRuns`). `fitMemberRun` tries only multiples of 10 and lets up to 9 unminted tokens sit after the last slot, since unseen tokens there would otherwise widen every slot to an odd size. A run is fitted only when the token right before it is a minted Z-collection token: after a neighbouring A slot, that slot's unminted last copy makes the start 1 low. A run holding a collection of a fitted drop is left to the drop grid. `applyGrids` tries the member grid only when the collection's own drop doesn't fit. Its `dropSpanOf` argument (`dropSpanMemo`, one per verifier run) shares drop fits across collections, since each run checks every one of its collections' drops. The verifier skips edge probes inside a fitted run too. Neither grid is sticky: a rediscovery that no longer fits falls back to the discovered ranges. Populate and the verifier log a `warn` whenever a write moves serials that were already set (`shiftedSerials`), so a dropped fit or a real boundary change shows in the log.
- Every path that rewrites one collection shares the same steps in `job/serial-batches.ts`: `fitRanges` (`refineBatches`, then `applyGrids`), `storeRanges` (ranges and fit marks in one transaction; unchanged ranges keep their row and only their marks are written) and `rewriteSerials` (serial updates with the `shiftedSerials` warning). Populate, the verifier's drift fix and `refine-serial-batches.ts` call them (the script only `fitRanges` in its dry run, all three under `APPLY=1`); change a step there, not in a caller. `fitDrop` loads and fits one drop for `script/drop-grid.ts`, `settleOpenDrops` and `dropSpanMemo`.
- `collection.grid_fitted_at` marks a collection whose stored ranges came from a fitted grid, for the API's serial estimate: any unmarked member keeps a drop under 7 days old (`OPEN_DROP_DAYS`, `@repo/lib/serial`) reading "at least". A write that stores one collection's ranges (`storeRanges`) marks only that collection, when its slot comes from a fitted run or from a fitted drop that is **start-pinned** (`loadDrop().pinned`: the token right before its start is another collection's mint), and clears it when its grid is gone; marking the rest would vouch for ranges they don't hold yet. Writes that store every member's slot (`applyGridWrites`) mark them all. A drop whose first member has not minted can fit the rest (Binary02 304A did in a holdout), and the pin catches it. A missing middle member can leave the rest fitting a wrong slot size that the pin can't see, so a drop must also be **roster-complete** (`loadDrop().complete`, `rosterComplete`): as many minted members as the season's largest other A drop of the artist. The first A drop of a season and subunit drops never are, so they stay unmarked and read "at least" for 7 days. The pin and the roster check gate only the mark and the open-drop step, never `fitDropGrid`, since Atom02 350A fits with an unminted token before it. `settleOpenDrops`, first in every populate run, fits each A drop under 7 days old that still has an unmarked member and, on a start-pinned, roster-complete fit, writes its slots, serials and marks (`planGridWrites` / `applyGridWrites`), so a drop closed by a foreign mint after its last member's settles within a run instead of waiting for a rediscovery.
- Review both grids with `script/drop-grid.ts` (all A drops and runs, one `season`, or `season collectionNo artist`). It reports each drop's and run's verdict (runs add unpinned and held, and flag more than 10 foreign tokens inside), its known serials matched before and after, and the serials that would change. It is a dry run until `APPLY=1`, which also marks fitted runs and start-pinned fitted drops; it reports a fitted drop that is not start-pinned. A fitted drop or run with no known serial is only as sure as the fit, as Cream02 348A shows: it fits, yet its HaYeon anchor is 6 above the grid.

## Banner backfill

`script/backfill-banner-compression.ts` re-encodes profile banners uploaded before the browser compressed them, to the targets in `@repo/lib/banner` (`sharp` for stills, ffmpeg with libx264 for GIF and video). It runs by hand on a machine with ffmpeg, never in the container, and is a dry run until `APPLY=1`. It points a profile at the new object with a compare-and-set on the old URL and never deletes the original; its done-log holds each old and new URL for a rollback. The rules are pure, in `lib/banner-backfill.ts`.

## Collection colours replay

`script/replay-collection-colours.ts` applies each slug's latest `collection_override` audit entry (app database) to its indexer `collection` row: a colour it sets goes on the row with the row's own kept as the source, a colour it reset goes back to the source. A dry run, with plain reads only, until `APPLY=1`, which locks each row, plans again under the lock, writes, and bumps `collection:modified-at`; it adds no audit entry. It reports slugs no collection has and rows with a staff colour but no history. Run it after an indexer resync from scratch, dry first. For a dry run against production, pass `PGOPTIONS='-c default_transaction_read_only=on'`.

## Price history

`job/snapshot-price-history.ts` runs hourly at minute 5 and on startup. It writes only today's UTC rows of `collection_price_history`, never touches a past day, and skips the run when the rate table is empty. It reads and writes the app database only, so it runs outside `if (indexerWrites)`.

## Trade verifier

A wrong copy's deadline, like expiry, stall reminders and the away grace, is due against `seenUntil`, never the clock, so an asked-for objekt sent before the deadline but read late still verifies the leg first. A specific leg whose objekt left the giver breaks only once `seenUntil` is `AWAY_GRACE_HOURS` past the move (`matchLegs`); until then `recordAway` keeps `away_at` as `recordStuck` keeps `untransferable_at`: set with one `away` note per move, cleared silently when the objekt is back. Every automatic accept (deadline, expiry, a broken leg's rescue, and every other open leg's pending copy when a break still ends the trade, `breakAcceptLegs`) goes through `acceptPicked` in `locked-trade.ts`, so the notes and progress stay the same whichever path accepts; a job that settles one trade takes its lock there too (`lockTrade`). A pending copy with a null `accept_by` gets its deadline from the worker the first time it sees the copy, not from the migration, so a copy recorded before the deploy still gets its full window after it.

A leg the receiver marked as received (`offer.confirmLeg`) is closed with `open = false`, so `loadOpenLegs` never matches it again, and has `verified_at` set with no `tx_hash`: the expiry, the progress counts and the unfinished rule read it as delivered without knowing it was confirmed.

`offerUpkeep` keeps `offer_item.sent_at` in step with the early send `itemStillHeld` counts (`earlySend`): `sentChanges` (`lib/offer-sent.ts`) sets it when the send appears and clears it when the objekt is back with its giver, which leaves the offer open. Both writes skip offers no longer open.

## Want alerts

`job/want-alerts` keeps its progress (cursor and state) in the `worker_progress` row `want-alerts`, saved in the same transaction as the alerts (`recordRun`), on every run. A worker reads and writes progress only in the database it alerts on, so a local worker can never move production's cursor. A missing row is a first run: it sets the cursor to `max(id)` and announces nothing already listed. Unreadable progress stalls the job with an error and never starts over.

The floor (`overlapFloor`) anchors on the previous run: the newest mark at or before the newest mark's time minus 10 minutes, so a gap between runs never shortens the late-commit window. `keepMarks` keeps marks by age with one-minute spacing and never cuts the anchor; a count cap would drop it in a crash loop.

Which partner lists may alert comes from `@repo/api`, the same as For you: `tradePartnerSql` (hidden, blocks, trade block) and `listedCte` (not idle) in `pairs.ts`. Change a partner rule there, never in the worker. An entry left out only because its owner cannot trade it yet (`unowned` from `selectAlerts`) goes into the state's `recheck` with the time it was first left out. Every run reads those entries again and keeps them for 24 hours, at most 20,000, dropping the oldest with a `warn` (`nextRecheck`).

Each alert type is Off, Any or Can swap (`notification_pref.match`, null reading as Can swap). For recipients on Can swap, `mutualQuestions` collects, per recipient and alert list, the partners that pass every other check. The job asks `mutualPartnerIds` (`@repo/api/services/trade/matches/recount`, For you's Mutual read live) over the lists that alert's link opens (`resolveCompareSides`), so the alert and the page agree. It runs four at a time, and a failed call counts as not mutual for that run, with one `warn`. That module is kept clear of `services/redis`, so keep it that way. `selectAlerts` alerts only the mutual partners and returns the rest as `notMutual`, which goes into the state's separate `mutualRecheck`: 24 hours, at most 5,000, so it never pushes out an `unowned` entry. A Sell only sale-list pair under Can swap is dropped without a recheck; a sale list that takes swaps (`takes_swaps`) is asked about like a have list. A recipient list with no pair (`AlertList.swapPair`, the SQL twin of `pickedSides`' pair in `context.ts`) can never make Can swap, so under Can swap `judge` alerts it on a swap match without asking, records the alert as Any, and skips a match that only buying makes (`wantsSwaps` false on the want list). A pair counts only when both halves can swap (the offering list offers swaps, the want list takes them), so a pair whose want list only buys is unlinked here. Each alert writes its choice to `payload.match`, which picks the link it opens.

## Want-list rules

`job/refresh-list-rules.ts` runs every 10 minutes and on startup. It re-expands every rule against the indexer's collections and its owner's holdings through `@repo/api/services/list/rules/expand` (env-free; keep it so), reading each described collection set and each owner's addresses once per run, and `bumpTradeVersion` the owners whose entries changed. It never touches `lists.updated_at`: the feed reads that as the owner's edit, so a refresh would keep an idle post listed and show it as updated. Unchanged rules take no lock and write nothing.
