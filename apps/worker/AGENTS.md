# worker

`Bun.cron` jobs registered in `src/index.ts` (`job/`), plus one-off maintenance scripts in `src/script/`. Scripts run against the production `.env`, and only some are dry runs by default (`APPLY=1` to write), so read a script before running it. Pure logic goes in `src/lib/` beside its test (`serial-math.ts` is the model).

From `@repo/api`, import only modules whose import chain stays clear of `env.ts`. `env.ts` validates the web app's whole `serverEnv` (Discord, S3, SES and more) as it loads, and the worker container has none of those, so the worker dies on start. `services/redis` imports it, and so does every module that imports `services/redis`, such as `services/market/currency-rates`. Before importing an `@repo/api` service, follow its imports. Read such tables directly with `db`, as `update-currency-rates` and `snapshot-price-history` do. `src/import-boundary.test.ts` fails when the bundle reaches `env.ts` or `services/redis`.

## One run at a time

Register every cron job through `safeRun(tag, job)` in `src/index.ts`, with the job's kebab-case log tag: it runs the job under the Valkey lock `worker:lock:<tag>`, so a second worker, or a slow run overlapping its next tick, skips. A shutdown frees the locks of jobs still running. The trade verifier takes its own lock and passes `{ lock: false }`. A long-lived subscription that must run on one worker only goes through `whileLeader` (`src/lib/redis-lock.ts`), as the activity relay does.

## Logging

Jobs log only through `log(tag)` (`src/lib/log.ts`). A run that changed something logs one `info` summary; a run that changed nothing stays silent. Per-item lines go to `debug`, shown only with `WORKER_LOG_LEVEL=debug`. A job running every few minutes adds its counts to a `heartbeat`, which logs one line an hour. Drift and failures that retry on their own are `warn`, one line per run with a count; a failed job, or a failure only a person can fix (an expired Cosmo refresh token), is `error`. `src/script/` prints to the console, since its output is the point. Every `log(tag).error` is also reported to Sentry (`instrument.ts` sets the sink); what is reported and the privacy rules are in `apps/web/AGENTS.md` (Error tracking).

## Held transfers

`job/collection.ts` (tag `fix-collection`, every 5 minutes and on startup) replays the indexer's `pending_transfer` rows once Cosmo returns a token's metadata: it creates the collection if new, the objekt, its transfers and the outbox rows for non-mints, applies and stamps the token's unapplied `transferability_update` rows, and deletes the held rows, in one transaction per token (`lib/pending-replay.ts` plans it). Transferability follows the same finality rule: the replay applies only final `transferability_update` rows, and each run then settles the rows left unapplied on objekts that exist, never over a newer applied change and never for a token with a change still in a hot block. Only tokens whose every held row is at or below `squid_processor.status` height replay: a hot block can still be reorged out, and the worker's write would survive it. The verifier's `seenUntil` stops one second before the oldest held transfer (`trade-verifier/indexer-head.ts`), so a held send never lets a deadline pass; that is why the replay runs every 5 minutes, since until it does every running trade and the staff console read the indexer as behind.

## Offline serials

Serial batches, anchors, the drop grid and drift checks keep their rules in `docs/offline-serials.md`. Read it before changing `job/serial-batches.ts`, `job/populate-serial.ts`, `job/verify-batch-boundaries.ts`, `lib/drop-grid.ts`, `lib/drift-candidates.ts`, `lib/serial-*.ts`, or the serial scripts under `script/`.

## Banner backfill

`script/backfill-banner-compression.ts` re-encodes profile banners uploaded before the browser compressed them, to the targets in `@repo/lib/banner` (`sharp` for stills, ffmpeg with libx264 for GIF and video). It runs by hand on a machine with ffmpeg, never in the container, and is a dry run until `APPLY=1`. It points a profile at the new object with a compare-and-set on the old URL and never deletes the original; its done-log holds each old and new URL for a rollback. The rules are pure, in `lib/banner-backfill.ts`.

## Collection media

`job/collection-media/` (tag `collection-media`, every 5 minutes and on startup; `index.ts` runs the phases, one file each: `keep-alive.ts`, `sync.ts` with `objekts.ts`, `apply.ts`, `transferable.ts`, `notices.ts`, and `run.ts` holds the run state they share) syncs connected Cosmo accounts' collections into the app's `collection_media` record, then applies the record to the indexer. It runs only with `indexerWrites` and `COSMO_SESSION_KEY`; without the key it warns once per start. It is the only writer of `cosmo_session` data and of the media columns of `collection` (`apps/indexer/AGENTS.md`, Staff colours on `collection`). Every run has three phases:

- **Keep-alive**, first in every run, only with `COSMO_SESSION_KEEPALIVE=on` (read once per start; off by default). Cosmo ends a web session after 45 to 60 minutes unused, so a live session whose `greatest(last_used_at, created_at)` is 20 to 25 minutes old (a fixed age per session id) gets one `users/me` request that reads only the status (`touchSession`). At most 20 touches a run, savable sessions (used under 45 minutes ago) first, then the rest, each longest unused first, inside the run's 50-request budget; a row is re-checked just before its touch. During a backoff at most 5, stopping at busy or unavailable (refused and unexpected skip to the next), and the backoff is neither cleared nor extended. With no 2xx yet in the run, 5 dead answers in a row, or outside a backoff 3 refused or unexpected in a row, stop the phase with one `warn` (counts only). A 2xx stamps `last_used_at`; a 401 or 403 with Cosmo's JSON error marks the session dead as the sync does; any other failure writes nothing and the next run tries again. The `info` summary gains `keep-alive ended: kept <hours> h; idle <n>` when a touch marked sessions dead (hours since connect, never an id), which is how Cosmo's absolute session lifetime gets measured.
- **Sync**, skipped while backing off. A live session is due when `sync_requested_at` is set or `next_sync_at` or `cookie_expires_at` has passed. Order: a session with a `sync_cursor` first, then requested ones (oldest request first), then scheduled ones by `next_sync_at`. All sessions leave from one IP, so the budget is global: 50 requests a run (`users/me`, every page and sign-outs), 4 minutes, one request at a time at least 1 s apart plus up to 500 ms of jitter, 40 pages per artist. A budget or time that runs out mid-session stores `{artist, page}` in `sync_cursor` and the next run resumes there. `last_used_at` is stamped only after Cosmo answers (`users/me`), never at the attempt. A finished sync sets `next_sync_at` 72 hours out plus a jitter from the session id. A 429, 5xx, timeout or firewall 403 is Cosmo-wide: the phase stops, and the backoff is 5 minutes doubling to 2 hours, kept in Redis (`collection-media:backoff`) so a restart does not reset it. An unparseable page parks that session for 6 hours with its cursor. A 401 or 403 with Cosmo's JSON error body is a dead session (`dead_at` set, cookie erased); any other 403 is `unavailable`, so one blocked egress kills no session. A cookie that fails to open (wrong `COSMO_SESSION_KEY`) is skipped for 6 hours with `last_error = key_unreadable`, never marked dead, since a wrong key would otherwise erase every user's cookie.
- **Apply**, every run, with no Cosmo call, so a backoff delays none of it: apply the record to the indexer, delete sessions dead for 30 days, and send the expiry notices. A notice claims its session through `UPDATE cosmo_session SET expiry_notified_at … WHERE expiry_notified_at IS NULL` (live rows with fewer than `RENEW_NOTICE_DAYS` left) and inserts the `cosmo_session_expiry` notification in the same transaction, so two overlapping runs notify once; the payload carries `expiresAt` only, never a nickname or address.

**Merge.** `mergeRecord` (`@repo/lib/collection-media`) takes a report into the record. Collection fields are the same for every holder, so alternating sessions must not flip a value: an empty field takes the first non-empty value, a null never clears one, `has_voice` once true stays true, and a different non-empty value replaces the stored one only when `confirmed_at` is over 7 days old.

**Apply rules** (`planMediaWrite`, under a row lock with `lock_timeout` 5 s, planned again under the lock, one transaction per row): `front_media` takes the record's `front_media_copy` only (our bucket's URL, never Cosmo's; with no copy yet the column keeps what it holds), `has_audio` goes false to true only, `back_image` and `accent_color` fill only a `""`, and `text_color` takes the record's `#rrggbb` only when `source_text_color` is null (no staff override) and it differs ignoring case. `background_color` and `source_*` are never written, and `band_image_url` is recorded but never written or copied, since `getBandImageUrl` reads the column before its hardcoded map. At most 50 back images are filled per run: a filled `back_image` changes the image hash, so `process-collection-images` reprocesses that row, and `backImageOnly` (`lib/image-sync.ts`) makes it fetch only the back image when the front and thumbnail were processed from the same front with no back. After a run that wrote, the job bumps `collection:modified-at` and deletes Spin's `held-by` key. Nothing here needs a replay script: after an indexer rebuild the next run writes the record back, copies included.

## Collection media copy

`job/copy-collection-media.ts` (tag `media-copy`, every 10 minutes and on startup, beside `process-collection-images`) copies each record's motion or voice file (`frontMedia`) into our bucket, so the site never serves Cosmo's URL. It does nothing, with one warn per start, unless `S3_BUCKET` and `S3_PUBLIC_URL` are both set, and it writes only the bucket and the record; the apply stays the one indexer writer.

- **Keys** are `collection-media/motion/<h>.<ext>` or `collection-media/voice/<h>.<ext>` (`voice/` when any record sharing the source is voice), `<h>` the first 32 hex digits of the SHA-256 of the source URL, `<ext>` from the sniffed type. The same source always gives the same key, so a retry overwrites its own object and a shared source is stored once; the folder never decides whether a copy is current. No Cosmo string other than that hash reaches a key.
- **Sources** must pass `acceptMediaUrl`: https, no credentials or port, at most 1,024 characters, host exactly `resources.cosmo.fans` or `imagedelivery.net`. The check repeats just before the fetch, and the host must resolve only to public addresses. A record whose slug is not an indexer collection is never copied.
- **Download rules**: a plain GET with no cookie, header or proxy, `redirect: "manual"` (any 3xx fails), 60 s per file, 64 MB cap enforced on the stream as well as `Content-Length`. The type comes from the bytes, never the response header (`video/mp4` brands include `qt  `, which is stored as `video/mp4`; HEIC and AVIF are refused).
- **Budget** per run: one download at a time, 20 attempts, 300 MB, no new download after 5 minutes, and a stop after 3 failures in a row (429, 5xx or timeout). A failure sets `front_media_failed_at` on every record with that source, retried after 6 hours, and the run logs hosts and counts by reason, never a URL. A success writes the copy URL guarded by the source it was made from, so a merge that replaced the source meanwhile is not overwritten.
- **No inline delete.** A key may be shared and the indexer row points at the old object until the apply runs. `script/cleanup-orphaned-collection-images.ts` sweeps both `collection-images/` and `collection-media/`, keeping every key an indexer `front_media` or a record's `front_media_copy` names, and deletes nothing when either holds a URL outside `S3_PUBLIC_URL`.

## Cosmo objekt data

The same pages carry each collection's `objekts[]`, and `recordPage` writes them to the app's `cosmo_objekt` with no extra request, cursor or budget. `observationsOf` (`lib/cosmo-objekts.ts`) keeps an entry only when `inventory.status` is `minted`, `inventory.owner` is the session's own address, and the indexer does not hold the token under another owner; one indexer read per page gives the holder check, `received_at`, `minted_at` and the collection. The run reads the indexer's final height (`squid_processor.status`) once before its first page request (a keep-alive touch may come first), so every chain change at or below it was indexed before Cosmo answered; without a height the run records no objekts. Rows name no user, session or address, are kept for good, and are untouched by disconnect, a ban, account deletion and the 30-day session cleanup. Grid use and `non_transferable_reason` are stored and shown nowhere; a later reader treats them as current only while the indexer's `received_at` equals the row's recorded one. Names follow Cosmo's terms (transferable, non-transferable reason), never "lock", which `locked_objekts` and the job and database locks own.

`COSMO_OBJEKT_WRITES` is a comma list read by worker and web (the estimate mark), each from its own environment (`script/cosmo-objekt-plan.ts` ignores it and plans as if every word were on): `anchors`, `untransferable`, `transferable`, parsed by `objektWriteModes` (`@repo/lib/cosmo-objekt-writes`). Unset records and reports only; an unknown word warns once. Changing it is an env edit and a restart of worker and web together. Run the plan script (read-only; it refuses a writable connection) on production before enabling a word.

**Confirmed serials.** A `cosmo_objekt` row with `serial_eligible` is a confirmed serial: an offline or pre-assigned token minted at or after `V1_CUTOFF_MS`, in the collection the read names, whose holder the chain confirmed at the read. With `anchors` on, `job/confirmed-serials.ts` loads them and `mergeAnchors` pins batches with them (`docs/offline-serials.md`), and `applyConfirmedSerials`, the last step of `populateSerialOffline` under the `serial-offline` lock, rewrites up to 20 collections with due reads per run.

**Transferable guards.** The apply phase judges up to 5,000 `transferable_due` rows a run (`judgeTransferable`, `lib/cosmo-transferable.ts`). A Cosmo read changes `objekt.transferable` only when all hold: the objekt's `received_at` still equals the one recorded with the read (not moved), no `transferability_update` is above the read's `chain_height` or unapplied, the owner is not cosmo-spin, and the row still holds the value the plan saw (compare-and-set, repeated in the `UPDATE`). Two directions, each behind its own word: `untransferable` (Cosmo false, ours true) writes only for the reasons `challenge-reward` and `welcome-objekt`, any other reason stays a `report_*` outcome; `transferable` (Cosmo true, ours false) contradicts the deliberate false rule and ships off. The breaker weighs the whole run before any write: when planned writes exceed min(200, max(50, 20% of judged reads)), nothing is written, the run stores the outcomes it did not plan to write, leaves the planned reads due, and warns with the counts. Re-arm earlier `report_*` rows by hand in slices of at most 50, since a larger slice trips the breaker. `cosmo_transferable` keeps, for good, each value the worker wrote or found in `objekt.transferable` under every guard, replaced only by a newer confirming read and marked superseded by a newer chain change. A repeated read re-judges only when it changed or its last judgement is 7 days old.

## Transferability correction

`script/fix-transferability.ts` compares every objekt's `transferable` with `isObjektTransferable` on chain and fixes rows the indexer took from Cosmo's class guess, from before it read the chain at mint (`apps/indexer/AGENTS.md`, Transferability at mint). It pins one final block B (`squid_processor.status`), reads every objekt minted before B's timestamp at B through Multicall3 `aggregate3` (500 per call), and skips cosmo-spin's objekts, which are `false` in the database and `true` on chain by design, and burned ones. A failed read counts as skipped. It reports mismatches by class and direction, overall and for the last 3 days of mints. The dry run refuses to start without a read-only connection, so pass `PGOPTIONS='-c default_transaction_read_only=on'`. `APPLY=1` writes a row only while it still holds the value read, its owner is not cosmo-spin, and the token has no `transferability_update` newer than B. A token with a `cosmo_transferable` record is held: Cosmo's value stays unless a `transferability_update` above the record's `chain_height` supersedes it, which the script marks on the record once its write lands (`cosmoHold`, `lib/transferability-check.ts`); the totals count tokens held by Cosmo and records superseded. It needs the app database migrated, since it reads `cosmo_transferable`. A full pass reads about 23M objekts in about 100 minutes at `RATE=8` calls a second. `LIMIT` samples, and `AFTER=<id>` resumes from an objekt id. The encoding and the comparison are in `lib/transferability-check.ts`.

## Trade post drift

`script/trade-post-drift.ts` checks what `trade_post` must hold whatever a post's pairing is (`packages/db/AGENTS.md`, Trade posts): a list on Trade in no row, a list in two rows, a row with the wrong owner or list types, and an offer whose `post_id` is another person's row. The rows are the only place a pairing is stored, so no check compares them with a second copy, and none compares hides with rows: a hide names a list and is valid whatever the rows say. It prints a count and up to 10 ids for each and exits 1 when any is above zero. Two more counts are printed as notes and never fail it, because neither is wrong data: an offer whose `post_id` row is now led by another list while its own list is still there (a merge can hand a row to the lead's old want list), and an offer on a list that leads a row with no `post_id` (made by the build before `offer.post_id`, or its row ended in a merge). Plain reads only, and it refuses to start without a read-only connection, so pass `PGOPTIONS='-c default_transaction_read_only=on'`.

## Price history

`job/snapshot-price-history.ts` runs hourly at minute 5 and on startup. It writes only today's UTC rows of `collection_price_history`, never touches a past day, and skips the run when the rate table is empty. It reads and writes the app database only, so it runs outside `if (indexerWrites)`.

## Trade verifier

A wrong copy's deadline, like expiry, stall reminders and the away grace, is due against `seenUntil`, never the clock, so an asked-for objekt sent before the deadline but read late still verifies the leg first. A specific leg whose objekt left the giver breaks only once `seenUntil` is `AWAY_GRACE_HOURS` past the move (`matchLegs`); until then `recordAway` keeps `away_at` as `recordStuck` keeps `untransferable_at`: set with one `away` note per move, cleared silently when the objekt is back. Every automatic accept (deadline, expiry, a broken leg's rescue, and every other open leg's pending copy when a break still ends the trade, `breakAcceptLegs`) goes through `acceptPicked` in `locked-trade.ts`, so the notes and progress stay the same whichever path accepts; a job that settles one trade takes its lock there too (`lockTrade`). A pending copy with a null `accept_by` gets its deadline from the worker the first time it sees the copy, not from the migration, so a copy recorded before the deploy still gets its full window after it.

When the verifier records a leg from a transfer it calls `removeReceived` (`@repo/api/services/list/received`) for the legs it recorded, in the same transaction, which takes the collection off the receiver's want lists that ask for it; `acceptCopy` does the same for a copy it accepts. See Received objekts in `packages/api/docs/offers.md`.

A leg the receiver marked as received (`offer.confirmLeg`) is closed with `open = false`, so `loadOpenLegs` never matches it again, and has `verified_at` set with no `tx_hash`: the expiry, the progress counts and the unfinished rule read it as delivered without knowing it was confirmed.

`offerUpkeep` keeps `offer_item.sent_at` in step with the early send `itemStillHeld` counts (`earlySend`): `sentChanges` (`lib/offer-sent.ts`) sets it when the send appears and clears it when the objekt is back with its giver, which leaves the offer open. Both writes skip offers no longer open.

## Want alerts

`job/want-alerts` keeps its progress (cursor and state) in the `worker_progress` row `want-alerts`, saved in the same transaction as the alerts (`recordRun`), on every run. A worker reads and writes progress only in the database it alerts on, so a local worker can never move production's cursor. A missing row is a first run: it sets the cursor to `max(id)` and announces nothing already listed. Unreadable progress stalls the job with an error and never starts over.

The floor (`overlapFloor`) anchors on the previous run: the newest mark at or before the newest mark's time minus 10 minutes, so a gap between runs never shortens the late-commit window. `keepMarks` keeps marks by age with one-minute spacing and never cuts the anchor; a count cap would drop it in a crash loop.

Which partner lists may alert comes from `@repo/api`, the same as For you: `tradePartnerSql` (hidden, blocks, trade block), `hiddenPostAtSql` (when the recipient hid the post) and `listedCte` (not idle) in `pairs.ts`. Change a partner rule there, never in the worker. A pair from a hidden post is read only when its entry was added after the hide and not by a rule (a rule's refresh inserts entries its owner never added), and comes back with `hidden` set: `selectUnhides` (`lib/want-alert-match.ts`) then brings the post back when the match is real (the offer's owner can trade a copy), whatever the recipient's alert settings, and `recordRun` deletes the hide in the alerts' transaction, before them, leaving a hide made after the run began; the job then bumps the hider's trade version, since their cached matches were built without the post. Its unowned pairs join `recheck`. A copy the wanter already holds never skips an alert or an unhide, in either direction, since For you never reads the wanter's copies and the two must agree; `judge` never reads `hidden`, so an alert goes out exactly when its post comes back, and a holdings test on one of them alone would alert for a post that stays hidden. A Can swap recipient's alert for a returning post comes one run later: `mutualPartnerIds` runs before the hide is deleted, so the pair waits in `mutualRecheck`. An entry left out only because its owner cannot trade it yet (`unowned` from `selectAlerts`) goes into the state's `recheck` with the time it was first left out. Every run reads those entries again and keeps them for 24 hours, at most 20,000, dropping the oldest with a `warn` (`nextRecheck`).

Each alert type is Off, Any or Can swap (`notification_pref.match`, null reading as Can swap). For recipients on Can swap, `mutualQuestions` collects, per recipient and alert list, the partners that pass every other check. The job asks `mutualPartnerIds` (`@repo/api/services/trade/matches/recount`, For you's Mutual read live) over the lists that alert's link opens (`resolveCompareSides`), so the alert and the page agree. It runs four at a time, and a failed call counts as not mutual for that run, with one `warn`. That module is kept clear of `services/redis`, so keep it that way. `selectAlerts` alerts only the mutual partners and returns the rest as `notMutual`, which goes into the state's separate `mutualRecheck`: 24 hours, at most 5,000, so it never pushes out an `unowned` entry. A Sell only sale-list pair under Can swap is dropped without a recheck; a sale list that takes swaps (`takes_swaps`) is asked about like a have list. A recipient list with no pair (`AlertList.swapPair`, the SQL twin of `pickedSides`' pair in `context.ts`) can never make Can swap, so under Can swap `judge` alerts it on a swap match without asking, records the alert as Any, and skips a match that only buying makes (`wantsSwaps` false on the want list). A pair counts only when both halves can swap (the offering list offers swaps, the want list takes them), so a pair whose want list only buys is unlinked here. Each alert writes its choice to `payload.match`, which picks the link it opens.

## Want-list rules

`job/refresh-list-rules.ts` runs every 10 minutes and on startup. It re-expands every rule against the indexer's collections and its owner's holdings through `@repo/api/services/list/rules/expand` (env-free; keep it so), reading each described collection set and each owner's addresses once per run, and `bumpTradeVersion` the owners whose entries changed. It never touches `lists.updated_at`: the feed reads that as the owner's edit, so a refresh would keep an idle post listed and show it as updated. Unchanged rules take no lock and write nothing.
