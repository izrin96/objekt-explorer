# Trade

Part of `packages/api/AGENTS.md`, which points here.

## Trade matching

### Can swap (Mutual)

- Mutual (Can swap) is `mutualOf` in `schemas/trade.ts`, which returns `counts.swap`: what the two can swap inside one post on each side. `swapScore` (`lib/trade-person.ts`, run by `matchCounts`) groups each swap match's `swapMyListIds` and `swapPartnerListIds` (the lists `trade` holds through, which `recount` fills; `myListIds` and `partnerListIds` also carry sale lists) by post pair and keeps the best pairing's smaller count, with that pairing's they-have count as `swapTheyHave` and the pairing as `swapPair` (the viewer's list ids in it and the person's post key, which is that feed post's `id`); the web's rules note (`swapThroughRules`) counts only rule matches inside it.
- A post key is the id of the pair's have or sale list: the viewer's come from `viewerPostOf` (`lib/trade-rank.ts`, over `pickedSides`, keyed only when the offering half swaps), carried on `Sides.postOf` by `resolveTradeSides`; the partner's from `partner_post` in `candidates.ts`, which pairs the two lists of a `trade_post` row when both are listed and the offering half swaps (`postPairsSql`). `recount` puts both maps on the partner as `posts`, so every `matchCounts(partner)` reads them. A list with no key counts one way only.
- `candidates.ts` computes its own pooled swap counts in SQL for the Mutual prefilter and order, a superset of the per-post rule that the recount then narrows.

### Which lists swap, and Open to

- A list offers swaps when it is a have list, or a sale list with `takes_swaps` (Sell or swap): one predicate, `offersSwapsSql` (`lib/trade-sql.ts`) and its TS twin `offersSwaps` (`schemas/open-to.ts`), locked together by `lib/trade-sql.test.ts`, which `offerMatchesWantSql`, `candidates.ts`, the feed's `postsCte`, `TAG_WHERE` and match index, and the viewer's `tradeHave` all read.
- A Sell only sale list never counts toward Mutual, though it counts toward the one-way counts (`theyHave`, `youHave`), so a person matched only through such lists is One way.
- A candidate entry carries `swap` and `sale`, and a Sell or swap entry can be both; `recount` judges haves on `swap` (an entry cached before it reads `swap` as `!sale`) and sales on `sale`.
- A want list's Open to is two booleans: Swaps only is `match_have` true and `match_sale` false, Swaps or buying both true, Buying only `match_have` false and `match_sale` true; `lists_open_to_something` keeps them from both being false, and `resolveOpenTo` (`schemas/open-to.ts`, beside `openToOf` and `flagsOf`, the one decode of the two booleans into Swaps only, Swaps or buying and Buying only; `byOpenToSql` in `lib/trade-sql.ts`, which the Browse match index uses, is the SQL twin of `pickByOpenTo`, locked by `lib/trade-sql.test.ts`) is what list create saves; after that a want list's Open to is the post composer's while the list is on Trade, and `list.edit`'s optional `openTo` while it is off (`openToEdit`, same module). A sale list's Open to is `takes_swaps`: `list.create` and `list.copy` take `takesSwaps` (default false) and store it only for a sale list bound to a profile (`writeList`, so `lists_takes_swaps_sale_only` holds), and `list.edit`'s optional `saleOpenTo` (`sell` or `both`) sets it for a bound sale list off Trade (`saleOpenToEdit`, same module: keep for any other list, an unbound one or one on Trade; refuse Sell only on a paired one with `list_sale_links_sell_only`).
- A want list linked to a have list is never Buying only: `pairRefusesOpenTo` (same module) is the rule, and `checkLinkedList` refuses it with `list_pair_buying_only` on list create, as `openToEdit` does on `list.edit` for a paired want list off Trade (every pair refusal is decided by the pure `pairRefusal`, `lib/list-pair.ts`), reading the want side's Open to (the flags a want list is about to save, or a have list's partner's), so a WTT pair's want side always takes swaps.
- A have list counts in a direction only against a want list open to swaps (`match_have`), a sale list only against one open to buying (`match_sale`), and `offerMatchesWantSql`, `candidates.ts`, `recount`, and Browse's `Viewer` indexes (`tradeWant`, `saleHave`) all apply it.
- A chip popover names only the lists that produced the match (`myListIds`). Ranking, Mutual only and the web chip all read it.

### Rankings and their caches

- `trade.people`'s per-person chip reads the matching pipeline through `personMatches` (`services/trade/matches/person.ts`, over `recountPartners`), so a change to the matching rules lands in one place. Its Mutual reads the Mutual people through `getMutualPeople` (`services/trade/matches/mutual.ts`, over `mutualPeople` in `lib/trade-rank.ts`), and its One way the people ranked by the sum of both counts through `getOneWayPeople` (`services/trade/matches/one-way.ts`, over `recountPartners(…, "all", { order: "sum" })`): no slice and no idle tier. The read loops are `readBatches` (`lib/trade-people-order.ts`), tested there.
- Both feed rankings recount up to `FEED_CANDIDATE_LIMIT` (1000) candidates, cut in SQL by the ranking's own order (`fetchTradeCandidates`' `order`) before the ownership check; `personMatches` keeps `CANDIDATE_LIMIT` and the filter's order, which for `all` is the swap score first, as `rankPartners` ranks.
- The rankings are cached for 5 minutes and refresh separately, so a person can leave Mutual or the One way set between two loads; the stored people order below keeps a scroll steady across that.
- Every Redis read on this path goes through `redisFailOpen` (`services/redis.ts`), as `getCache` does, so an outage costs the cache, not the feed; while Redis is unreachable `getCache` keeps values in process (`LOCAL_MAX_ENTRIES`), so upstream calls still run once per TTL per process.
- Compare with narrows the viewer once through `narrowViewer` (`lib/trade-viewer.ts`), so chips, rings and filters share it.

### The people feed and handles

- `trade.people` is what the web reads: it pages by person (`PEOPLE_PAGE_SIZE` 12, each row every post the feed keeps for that person, `peopleFeed` in `services/trade/feed/people.ts`) through a stored order.
- A first-page `person` skips the order and returns only that person's row, or none, with no cursor: the person and post pages read their row this way, not a URL parameter. `lead` in the cursor only serves cursors from before that.
- Each row carries the person's `handle`, as do `trade.myPosts` (the viewer's own) and a post card's `owner`: `tradeHandle` (`schemas/trade-person.ts`, tested, beside `defaultProfile`), the default profile's nickname, else its address, lower-cased, null with no linked profile.
- `trade.person` (`services/trade/person.ts`, under `limitFeed`) turns a handle (any linked nickname or address, any case, through citext; an old `user_address` row keeps its nickname, so two accounts can share one: `handleOwner` (`schemas/trade-person.ts`, tested) picks the account whose own handle it is, else a default profile first, then the newest linked row) or an older link's user id into `{ userId, handle }` with the canonical handle, or `NOT_FOUND`, also for an account with no linked profile.
- Each have or sale side carries `first`, its list's first collection in the list's own order whatever the viewer rings (`firstSlug`), for a shared post's preview image.

### The stored people order

- Page 1 builds the whole order (`buildOrder`; `buildPeopleOrder` in `lib/trade-people-order.ts`): Browse by newest bump, Mutual only the Mutual people with a kept WTT post, Any those, then the One way people with a kept post, then everyone else by bump. A person keeps their first place, so a Mutual-ranked person with no kept WTT post lands in One way.
- It is stored for an hour (`savePeopleOrder`, `services/trade/feed/scope.ts`, `trade:people-order:3:<viewerId|anon>:<token>`, the token a hash of the order so a reload or every signed-out reader shares one key, bound to `ordersFingerprint` of the filters, mode, Compare with list and lead), and later pages read it by position (the cursor's `order` and `at`), so a ranking or a bump that changes mid-scroll moves no one; the rankings and kept-post checks run only when the order is built.
- A person whose posts all emptied is skipped where their place comes.
- Past `ORDER_LIMIT` (2000) the tail goes on by the `(bumpedAt, userId)` keyset from the order's `more`.
- When the order is gone or was built for other filters, the server builds it again and goes on by `resumeAt`: after the cursor's person, else at `at`. The cursor carries `bumpedAt` and `userId` for that and for the keyset past a capped order.
- A request makes its first stage-2 read and at most `EXTRA_PEOPLE_READS` more (`readBudget`, `lib/trade-people-order.ts`), so sold-out people can't chain recounts; `at` moves past every person read, kept or emptied, so a short or empty page still moves on.

### Partner rules, hidden and idle posts

- The partner side of a match is `tradePartnerSql`, `inHiddenPostSql` and `listedCte` (`services/trade/lists.ts`, `services/trade/feed/query.ts`), shared with the worker's want-list alerts (which read the hide through `hiddenPostAtSql`, the same predicate with its time), so a partner rule changes there for both; a new Trade read that applies `tradePartnerSql` applies `inHiddenPostSql` too.
- A hide is a row of `hidden_trade_post` that names a post's `trade_post` row (`post_id`) and covers the lists of that row, its lead and its want list, whatever their Trade state. It follows the row's lead through writes: when a write deletes a row or hands it to another list, `planPostRows` reports a move (`moves`) to the surviving row that now holds the old lead, and `writePosts` applies it. So a hidden Buy post that is later paired stays hidden as the pair (the hide moves to the merged row), a pair whose have list is deleted while its want list is on Trade stays hidden as the re-led Buy post, and after an unpair the lead's row keeps the hide while the want list's new post shows. `list_id` is the anchor the hide was made on, kept only for builds before hides moved to rows (`packages/db/AGENTS.md`, Trade posts). `services/trade/lists.ts` states the rule in two forms that must change together: `coveredListsSql` (behind `inHiddenPostSql`), the set of lists a viewer's hides cover, which the feed and match candidates read, since a set is hashed once per statement; and `hidesOfSql`, the hides whose row holds one list, which the worker's alerts (`hiddenPostAtSql`) and both deletes read. The lookup form over the feed's `posts` costs about ten times the set form for a viewer with hundreds of hides, so keep the feed on the set. `hidePost` writes the anchor's row (`postRowSql`), and the primary key `(user_id, post_id)` refuses a second hide of one post. `feedWhere` drops a hidden post unless `skipHiddenPosts` is false, which `peopleFeed` sets for a first-page `person` read, so the person and post pages keep it, counted, with `hidden` set. A hide ends three ways: Unhide (`unhidePost` removes the viewer's hide of the row that holds the named list), the worker's want-alerts job, when the post's owner adds an entry by hand after the hide that matches a list of the person who hid it (`hiddenPostAtSql`, `hidesOfSql`), and the row ending (the `post_id` cascade), which a hide escapes only by a move. The job bumps that person's trade version, as Unhide does.
- Matching candidates (`candidates.ts`) count only lists inside a listed post, so an idle list counts toward nobody; the viewer's own lists count whether listed or not.
- The idle rule (`listedPost`) reads a post's bump from its rows' sides and its change time from its lists' `updated_at`, the list's content time, which every post that holds the list shares.

### Near matches

- A near match (a collection that would count if one side's Open to allowed it) comes only from the viewer index: `nearFor` (`lib/trade-viewer.ts`) is set differences of the `Viewer` sets beside `indexFor`, so the two change together and a match is never near. It rides on the viewer's reads only (strip items and `side.near`, `trade.sideItems`, `trade.listMatches`, `offer.suggest`'s `near` through `personNear`, the picker's `tags` through `pickerTagsFor`) and never enters the recount, the rankings, their caches, alerts or chat cards.

### Cache versions

- The ranking caches carry a version (`trade:mutual-people:10`, `trade:mutual-count:9`, `trade:oneway-people:6`, `trade:person:10`, `trade:people-order:3`); bump it when the cached value changes shape or meaning.

## Trade posts

A post's pairing is read from `trade_post`, one row per post (its lead list and at most one want list), and so are the Trade state, bumps and Open to of the reads that build posts and match against them (see below). Every read outside a write path takes the pairing from the row: `postPairsSql(post, lead, want)` (`services/trade/lists.ts`) is the one pairing rule over a joined row, and `postPartnerSql(alias)` gives a list's other half, with no condition of its own, wherever a read needs a list's partner as data (`feedListColumns`, `resolveTradeSides`, `inPostsOf`, the picker's `postWantedAmong`, `partnerListChoices` and `postListsOf`, `reportedPost`, `fetchHiddenPosts`, the worker's `swapPair`); `PublicList.linkedList` comes through the `postLed` and `postWanted` relations (`pairedListOf` in `services/list/read.ts`). The pure modules still call their input `linkedListId`; the server fills it from the row. A row pairs more than a post does (an off-Trade pair is a row), so a read keeps its own Trade-state, owner and Can swap conditions. The rows are the only place a pairing is stored. `lists.linked_list_id`, the link they replaced, is dropped (`packages/db/AGENTS.md`, Trade posts). The pure modules, `list.find` and `createListInputSchema` still call a list's partner `linkedListId`, a name open tabs read and send. Every writer of a pairing, of `discoverable`, or one that deletes a have, sale or want list (`trade.savePost`, `trade.takeDownPost`, `writeList` for `list.create` and `list.copy`, `deleteList`) takes `lockPosts` (`services/list/shared.ts`) first: `lockTradeLists`, then a fresh read of the person's lists and rows in a statement of its own, because the locking statement returns only the lists that existed when it began and may have waited for a writer that created one. `planPost` and the refusals read the locked lists, each with its partner by the rows; the plan starts from the fresh read. After its list writes the writer hands its change to `writePosts` as a `PostChange`: the pair to make, the lists to unpair, the post it edits or takes off Trade (`post`, with the lead an edit leaves in it), the Trade state it sets per list (`sides`, side intents), a list it created, and the lists it deletes. `writePosts` runs the pure `planPostChange` (`lib/trade-post-rows.ts`), writes the row operations, then the lists' `discoverable` and `bumped_at`, and returns the lists whose partner changed, for `touchList`. `planPostChange` plans only the rows the write is about, its component (`componentOf`): the post's row, and the row of each list the write names (its row in the edited post when it is there, else `postRowOf`), plus every row of a deleted list, each as a component of its own. It runs today's rules over each component (`partnersOf`, `applyPairing`, `planPostRows`, where a list is on Trade when the write's intent says so, else when its side in the component was) and leaves every other row as it is, state included, so the planner holds a list in several rows. A list in two rows of one component throws (`a list in two rows of one write`): drift check 2 keeps production at one row per list, and `planPost` still refuses a list that is in another post (`trade_post_list_in_post`), so `trade.savePost` never sends `newPost`, the input that puts a post in a row of its own beside a list's other rows. Whole-set repair is gone: a write leaves the rows it does not name, so a row a missed writer left wrong stays wrong until drift finds it. A post keeps its row id while it stays one post: the planner never deletes a row and inserts another that holds one of its lists, it changes the row's lead instead (a Buy post that gains a have list with no row; a pair whose lead is deleted while its want list is on Trade). Merging two posts ends one id: the lead's row stays, unless the want list was on Trade before the write and the lead was not, in which case the want list's row stays and takes the lead (a Buy post on Trade edited into a swap with a have list that was off Trade keeps its id, over the row that have list left behind); a split leaves the lead its row and gives the freed want list a new one. Edit post keeps its row whichever of its lists it swaps or drops: `planPost` returns the edited post's anchor (`replaced`) and the list that leads the post after the save (`lead`), `trade.savePost` names the edited row by `postRowOf(replaced)`, and `planPostRows` hands that row to `lead`, so the post keeps its id and its hides; the list the row led keeps a row of its own, off Trade, as any lead does, and a row `lead` led before goes, its hides moving to the edited row. `deleteList` therefore calls `writePosts` with `removed` before it deletes the list, so the row is re-led while both lists exist. `writePosts` moves hides (`moves`) before it deletes rows, since the `post_id` cascade would take them first; `trade-post-rows.model.test.ts` asserts the rule on every random write. Pairing A with B takes each from its old partner, who is left with none. A new such writer goes through `lockPosts` and `writePosts`. `lib/trade-post-rows.model.test.ts` runs the link writes of the build before against these over random writes and requires the same lists, rows and touched lists; it runs no SQL, so a change to a writer's statements is proven by running them. `anonymizeUser` needs no call: the rows go with their lead lists. A row is kept through Take off Trade, and a link is a row whatever its lists' Trade state. A want list pairs with a have list, or with a sale list that takes swaps (`checkLinkedList` refuses a Sell only one with `list_sale_links_sell_only`); `groupPosts` and `postsCte` fold either kind of pair into one post (in SQL through `postPairsSql`, which `postsCte` and `candidates.ts`' `partner_post` share), and a sale post with swaps is tagged WTS then WTT, then WTB when its want side is open to buying (a Sell post's "also pay", saved as the want list's `match_sale`, as on a Swap post). `schemas/trade-post.ts` is the one source of post kinds (Swap, Sell, Buy) and tags, pure and imported by the web: `tagsOf` (WTT for a have list or a want list open to swaps, WTB for a want side open to buying, WTS for a sale list; WTT before WTB, and a sale post leads with WTS), `postKindOf`, `groupPosts` (which `pairPosts` in `lib/trade-posts.ts` wraps), and `planPost`, which turns a composer choice into the writes or a `TRADE_POST_REFUSALS` code. `TAG_WHERE` in `lib/trade-sql.ts` is the SQL twin of `tagsOf`, locked by `lib/trade-sql.test.ts` (a table of post rows through `tagsOf`, the rendered SQL pinned beside it): its `wtb` reads the pair partner's `partner_match_sale`/`partner_match_have` from `postsCte`, for a pair anchored on a have or a sale list, and its `wtt` reads no partner column, since `excludeWttOf` negates it. Feed posts and `trade.myPosts` carry `tags`; chat post cards carry `tag` only, the first tag. `trade.savePost` and `trade.takeDownPost` (`services/trade/post.ts`) lock the poster's have, want and sale rows `FOR UPDATE`, run `planPost` on them and write in one transaction, then `touchList` every changed id. A Swap post with one list, or a Sell post that takes swaps, keeps that list's pair; any other split of a pair needs `unpair`, except that a list an edit drops from the post is unlinked from the half that stays. Taking a post off Trade keeps its link. `list.edit` takes no Trade state for any list type: a list's link and `discoverable`, and a want list's Open to while it is on Trade, belong to its post, which `trade.savePost` writes, and the `discoverable` a tab from before this rule still sends is stripped by the input schema; off Trade a want list's Open to is `list.edit`'s `openTo`, written as a `CASE` that keeps the stored flags if the list went on Trade, or was linked while the new value is Buying only, since it was read. A bound sale list's `saleOpenTo` is written the same way (`takesSwapsColumn` in `services/list/edit.ts`): the `CASE` keeps the stored `takes_swaps` if the list went on Trade, or was paired while the new value is Sell only, and a Sell only write runs under `lockTradeLists` like a Buying only one.

A row also holds each side's Trade state and bump (`lead_on_trade`, `lead_bumped_at`, `want_on_trade`, `want_bumped_at`) and the post's Open to: `match_have` and `match_sale` of its want side (the want list, or a want lead) and `takes_swaps` of a sale lead. Each row's state comes from the write (`rowStateOf`): a list the write names takes its intent's on or off; its bump stays when its side was on, and a turn-on takes `bumpAt`, the person's turn-on bump time (`turnOnBumpedAt`), which `lockPosts` reads once after the lock as text, the form the bump columns arrive in; Open to and `takes_swaps` come from the intent, else from the list when the intent turns the side on from off, else from the row the list was the open list or sale lead of, else from the list. A list the write does not name brings the side it had in the component, so a list moving into another row keeps its post's state; a list with no side yet comes in off. So `savePost` passes on for each picked list (with the want list's Open to and the sale list's `takes_swaps`) and off for each dropped one, `takeDownPost` off for the post's lists, `writeList` on for a list created on Trade and the partner it turns on, `deleteList` none. An insert carries its state and `writePosts` writes every other changed row in one `UPDATE … FROM unnest(…)`. `lists.discoverable` then means "on Trade in some post" and `lists.bumped_at` is the latest bump of the list's sides, compared by time, since two bump texts may carry different UTC offsets: `planPostChange` returns them for each list of the write whose value changed (`ops.lists`), and `writePosts` writes them last, in one `UPDATE lists … FROM unnest(…)`. The writers write neither; `writeList`'s insert still sets both, since the list exists before its row. `savePost` still writes a picked want list's own Open to and a Sell post's `takes_swaps` to the list: the list's values off Trade and the composer's start. `bumpPerson` bumps the lists and the sides that hold them in one statement under `lockTradeLists`: without the lock, the row half reads the snapshot the statement began with and would miss a row a post writer inserted while the list half waited. `list.edit` writes Open to and `takes_swaps` only off Trade and leaves the row's copy as it is while the side stays off, since a write no longer repairs rows it does not name: no read takes an off-Trade side's Open to, and writing the row there would need the lock on every off-Trade save. A later turn-on with no Open to in its intent takes the list's own, so a stale value never goes live. The reads that build posts and match against them take Trade state, bumps and the post's Open to from the rows: `postsCte`'s `on_trade` is `onTradeSql` (`services/trade/lists.ts`, over `onTradeRowsSql` in `lib/trade-sql.ts`), one row per list side on Trade, which match candidates' `partner_lists` and the worker's want-alert pairs read too; `feedListColumns` reads a list's bump, Open to and `takes_swaps` through `postStateSql` (the side of the row `postRowSql` names, Open to and `takes_swaps` only while that side is on Trade, else the list's own); `fetchOwnTradeLists` keeps a list with a side on Trade (`sideOnTradeSql`). Both follow one type rule: a want list's Open to and a sale list's `takes_swaps` come from the row, every other list's from itself. Reads that ask about a list as such stay on `lists`: the Marketplace, offers and the picker, chat cards, the list page, `visibleOnTrade`, hides, the viewer's own lists and Open to, `personBumpedAt` and `lastBumpOf`, and the report snapshot. `apps/worker/src/script/trade-post-drift.ts` checks each list's `discoverable` and `bumped_at` against its rows (check 5) and each row's Open to and `takes_swaps` against the post rules (check 6).

A post's id is its row, read through `postRowSql` (`lib/trade-sql.ts`) and its twin `postRowOf` (`lib/trade-post-rows.ts`): the lowest row the anchor list leads, else the lowest row it is the want list of, since a want list on Trade can sit in a row led by an off-Trade have list. Feed posts and `trade.myPosts` carry it as `postId`, beside `id`, which stays the anchor list's id, as `swapPair.theirPostId` does. `postId` is null only when the rows drift. No input takes a post id.
