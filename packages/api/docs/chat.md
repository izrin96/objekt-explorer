# Chat

Part of `packages/api/AGENTS.md`, which points here.

## Chat: the first message is the start

`chat.start` only opens a conversation row and marks the caller's `conversation_member.opened_at`; it counts nothing and sends nothing. It also returns the thread's newest page (`loadThread`, `null` when that read fails) for the web to seed its cache with, so a Message click opens the thread in one request. A conversation's first message or offer is its start: `appendMessage` runs the `first` callback (`openFirst`, `services/chat/start.ts`) under the row lock when `last_message_id` is null. `openFirst` re-runs `startVerdict` (Nobody, bans, blocks, mute, the start limit read from `conversation.started_by/started_at`) and stamps `started_by/started_at`. Any path that may append a first message takes `lockStarts` (the sender's advisory lock) before the conversation row lock, never after (`sendMessage`, `createOffer`, `checkStart`). Where a first message lands is the caller's verdict: `sendMessage` and `createOffer` pass `listed` to `appendMessage`, from the pure `firstListed` (`lib/chat-rules.ts`). A card through the recipient's sale, have or want list (every post card) or an offer that asks through their lists or gives a collection on their want list is listed. Anything else, a missing `listed` included, puts the recipient in Requests, whoever opened the conversation. `acceptOffer` applies the member `accept` event (`updateMemberIn`, after the conversation lock), so a deal taken from Requests moves it to the Inbox. An empty conversation opens as a thread only for a member with `created_by = me OR opened_at IS NOT NULL` (`visibleToMember`), and no conversation list shows it (`selectConversationRows` requires `last_message_id`), so a Message click that sends nothing leaves no row in anyone's inbox; the next click reuses it. `resolveCard` checks the listing and the holder through `cardAllowed`, and `hydrateCards` takes the viewer so a hide-serial list shows no serial or objekt id to anyone but its owner.

## Chat: requests and the icon's dot

Requests add no number to the Messages icon, but they set its dot: `hasUnseenRequests` (`services/chat/inbox-counts.ts`, served as `chat.requestsUnseen`) is true while a request's `lastIncoming` message has an id above `message_pref.requests_seen_message_id`. `chat.seeRequests` moves that marker forward (`greatest`, computed in SQL at write time) when the web opens the Requests tab. Every `chat_message` event carries the viewer's `requestsUnseen`, so a new field on that event must be filled in `buildChatMessages` (`services/chat/live.ts`), beside `unread` and `requests`.

## Chat: deals

A conversation's row and thread carry its `deal`: the most urgent of its open offer, running trades and trades still to rate, since one conversation can hold several at once. `readDeals` (`services/chat/deal.ts`) reads them for a page in one statement and runs `rateRefusal` itself; the pure `dealOf` (`schemas/chat-deal.ts`, tested) picks a Needs you state first, then any other live one, then one to rate, the newest offer winning a tie. A running trade's step comes from `tradeStep` (`schemas/trade-step.ts`, tested), which the web's `stepKind` calls too, so the order lives there. A new step that waits on the viewer also joins `NEEDS_YOU_STATES` and `needsYouSql` by hand; typecheck then points at the web's banner, words and tones. `needsYouSql` (`lib/needs-you-sql.ts`, pure, with `pendingCopy`) is the SQL twin of `NEEDS_YOU_STATES`, and `lib/needs-you-sql.test.ts` locks the pair (a table of deals through `dealOf`, the rendered SQL pinned beside it), so change both and the test together. It serves both `chat.list`'s `show: "needs-you"` and `chat.inboxCounts`, which leaves out muted conversations as the Messages icon does. `unreadCount` and `deal` are filled in `toConversationRows`, so the list, `loadConversationRow` and every `chat_message` event carry them; both have schema defaults, so an event from the previous build still parses.

## Chat: replies

`message.reply_to_id` names the message a reply answers: a bare id, checked by `sendMessage` to be a text or card message of the same conversation (`invalid_reply` otherwise). `ChatMessage.replyTo` is built at read time in `toChatMessages`, from one read of the quoted rows joined through each reply's own conversation, then the pure `quoteSourceOf` and `replyQuote` (`schemas/chat.ts`, tested), so a quote follows an unsend made after the reply and never carries unsent text or card; a missing row reads as unavailable. Every `MessageRow` source (`loadThread`, `appendMessage`'s return, `findSentMessage`) selects `reply_to_id`, or that path's messages lose their quote.

## Chat cards

A message holds an objekt card or a post card (a Trade post, by its list). `message.card` stores either with its `kind`: `{ kind: "objekt", collectionSlug, objektId?, listId? }` or `{ kind: "post", listId, match? }`; search reads `card->>'collectionSlug'`. `storedCardSchema` is the union, read through `parseCard`. Every output carries a card with its `kind`: `ChatMessage.card` and `ConversationRow.context` are the objekt or post view, `ConversationRow.last.card` names the kind, and the `chat.start` result's `card` holds the input, view and collections of either. A card input names its `kind`. Offer and trade items are drawn as objekt cards through `hydrateCards`, which takes a `CardRef` (an objekt card without its `kind`). A report excerpt entry keeps its message's card the same way, a post card by its list only (`card: { kind: "post", listId }`), so it shows what was shared and not the match.

`resolveCard` accepts a post card for a list the partner owns that is shown on Trade and not trade-sanctioned. With `withMatch` it saves the match from `personMatch` (`services/trade/matches/index.ts`): the owner's collections on the sender's wants, then the sender's on the owner's, each as a count and the first three slugs in the person sheet's order, and `canSwap` (`mutualOf` above zero), which the web's first-line suggestion reads; a card saved before it has none and reads as Can swap. The client only asks. `fetchPostCards` (`services/trade/feed/post-cards.ts`) reads the post live: either half of a have and want pair names the post that holds it now, a list gone or off Trade reads as removed, and a saved match stays as saved. Post cards and matches name collections, never serials.

A report can name a Trade post (`postListId`, either half of a pair). `report.post` holds a snapshot (`reportPostSchema`: its tags, each list's name, type, slug and description, and whether it was on Trade, built by the pure `postSnapshot` in `lib/report-post.ts`) plus the anchor's `listId`, with no foreign key, so it outlives an edit, the list and the account. `fileReport` refuses another account's list or a non-trade list with NOT_FOUND, and files without the post when the list is already gone. Staff read the post as it stands through `staffPosts` (`services/trade/feed/post-cards.ts`), never `fetchPostCards`, which hides what a block or sanction hides.
