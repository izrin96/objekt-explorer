# Lists

Part of `packages/api/AGENTS.md`, which points here.

## Lists

`writeList` (`services/list/create.ts`) is the one place a list row is created: `list.create` and `list.copy` both run `prepareList` first, outside any transaction (validation and partner reads use the pool, so a transaction waiting on them would hold a connection), then `writeList` inside theirs, which picks the profile slug on the transaction's own connection right before the insert. It returns the ids to `touchList` after commit. A change to a link touches two lists, so every writer of one takes `lockTradeLists` first (`services/list/shared.ts`: the user's have, want and sale lists, `FOR UPDATE` in id order): `writeList` when it links, re-checking the partner with `pairRefusal` under the lock, `list.delete` and `anonymizeUser` (`ON DELETE SET NULL` locks the partner), and `trade.savePost` / `takeDownPost`. Any other order deadlocks against them. A copy's entries come from `planCopy` over the pure `lib/list-copy.ts`; it checks that the caller owns the target profile before it reads that profile's holdings from the indexer, so `list.copyPreview` cannot read another user's holdings. `copyMode`, `needsHoldings`, `carriesPrices` and `copyUnit` live in `schemas/list-copy.ts` because the web dialog imports them: it asks `copyPreview` for a count whenever the mode is not `rows`. `list.slugPreview` fills the edit form's URL field with the `generateProfileSlug` call `list.edit` makes, so a change to how a profile slug is made lands in one place; `profileSlugBase` lives in `lib/profile-slug.ts`, not `schemas/list.ts`, because `slugify` is CommonJS and a `schemas/` file that imports it ships it to the browser even where nothing calls it.

A list description goes through `normalizeUserText` (`schemas/common/user-text.ts`, tested), shared with the profile bio: `createListInputSchema` and `editListInputSchema` run it on write (so `list.copy` too), the web form runs it before sending, and `fetchList` and the feed's `toListLink` run it on read, so a row saved before it shows clean. It removes control characters, text-direction marks, spaces at line ends and blank lines at the start and end, turns a tab into a space, and returns null for text that is only spaces or default-ignorable code points; indentation, runs of blank lines and filler rows (blank Braille, Hangul filler) stay, since people decorate with them.

A trade ratio (`ratio` on `lists`, `list_entries` and `list_rule`: 2 to 5, null for 1:1; `schemas/trade-ratio.ts`) is display only: nothing that matches, counts, ranks or alerts reads it, and only have and want lists take one. An entry's is set by `list.setRatio`, which checks every id (a rule's entry or one off the list refuses `list_ratio_entry`) before it writes, then calls `touchList`, so it is not a bump. The list's Ratio for all is `list.edit`'s optional `ratio`; omitted keeps it, for tabs from before it. `listEntries`, `fetchList` and `list.rules` return each row's own value; the feed (`FeedEntry.ratio`, `coalesce(entry, rule, list)`, cached under `trade:post:4`, left off a side that doesn't swap) and the picker's get side (`allowedEntries`, have lists only) carry the one that applies. A copy keeps ratios only into the same type (`carriesRatios`).

`trade.sideItems` pages a side `SIDE_PAGE` (200) collections at a time through `fullSide`'s offset, `matched` and `near` still counting the whole side. A sale page's prices, QYOP flags and notes are read straight from `list_entries` by the page's copy ids and folded by `stackAsk` (`lib/trade-feed.ts`, tested), never carried on `FeedEntry`, so the post-entry cache and the feed stay free of them.

## Want-list rules

A rule (`list_rule`) is a definition plus ordinary want entries: each collection it wants is a `list_entries` row with `rule_id` set, so matching, Can swap, the feed and want alerts read them unchanged. The pure logic (`expandRule`, `ruleProblem`, `ruleLabel`, `ruleLine`) lives in `schemas/list-rule.ts` because the web imports it. Expansion is `services/list/rules/expand.ts`, env-free because the worker's `refresh-list-rules` imports it: `syncRuleEntries` locks the rule row and applies `ruleEntryDiff` (`lib/rule-entries.ts`, tested), inserting and deleting, never rebuilding, so entry ids survive and `want_alert_sent` keeps a wanted-again collection from alerting twice. Reads split rules from objekts: `fetchListWithEntries`, list previews, copy, remove, the Discord format and the trade chat card skip `rule_id` rows, and `list.rules` serves the strip. The feed folds a want side's rule entries into `rules` tiles (`ruleTiles`), and `Viewer.ruleWant` names the collections the viewer wants only through a rule, for For you's lines (`ruleMatchesOf`). A rule's `ratio` sits beside its definition, never in `ListRuleDef` or `ruleDef`, so expansion and the worker cannot read it: `addRule` and `updateRule` take it beside `rule` (an update without it keeps the stored one), `detachRule` writes it onto the entries it frees, and a rule's own entries leave theirs null. A rule has no size limit (a set rule's class may be null, any class, so one artist alone reaches about 9,500 collections today); a list holds 20 rules.
