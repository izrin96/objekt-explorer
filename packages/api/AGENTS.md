# @repo/api

oRPC routers (`src/routers/`), Zod inputs (`src/schemas/`), and the services they call (`src/services/`). Pure logic lives in `src/lib/` beside its `*.test.ts`.

A procedure checks its input and the caller, then calls a service; database and Redis reads and writes live in the service. No router imports `@repo/db`. Services sit in their domain's folder (`services/objekt/`, `services/offer/`, `services/list/` and so on), and a new service joins the folder of its domain.

The worker imports some `services/` modules (`grep -r '@repo/api/services' apps/worker/src` lists them), and its container cannot load `env.ts` or `services/redis`. Keep those modules' import chains clear of both; `apps/worker/src/import-boundary.test.ts` fails when one is not.

## Round trips

A request spends as few sequential round trips to one database as its reads allow; the owner weighs this above a shorter function. Before adding an `await` on a query, ask what it waits for:

- **It waits for nothing: run it in parallel.** Reads that don't depend on each other share one `Promise.all` (`toProfilePage`, `offersMessage` in `services/list/read.ts`). A read that needs one field of another takes that read's pending promise, so both still start together (`activityBetween` takes `chatSafety`'s `blockedEitherWay` that way in `loadThread`; `toChatMessages` chains only the objekt cards onto the offers read).
- **It waits for a row only to filter by it: merge it.** Two reads of the same row, or a lookup whose result only filters the next read, are one statement: a relation `with` (`findHeldList`, `fetchListForViewer`), a join, or one `SELECT` of several `EXISTS` (`chatSafety`).

What parallel reads must keep:

- The refusal a caller gets: when two parallel reads can both refuse, use `Promise.allSettled` and rethrow in the old order (`prepareList`, `sendMessage`).
- Every started promise inside the `Promise.all` or `allSettled` that awaits it. A promise started earlier and awaited after another `await` becomes an unhandled rejection when that `await` throws first.
- Early returns: a path that ran no query (own list, the owner's Nobody setting) still runs none, so check the cheap in-memory conditions before starting the batch.
- A transaction's statements in sequence, in its documented lock order: one connection runs one statement at a time.

The app and indexer databases cannot join, so those reads run side by side.

## `/rpc` stays compatible with open tabs

A tab loaded before a deploy keeps calling `/rpc` with the input shape it was built with, so every input an older client sends must still validate to the same data. New input fields are optional with a default. Before changing an `.input()`, state what an open tab sends after the deploy and confirm it still validates.

When `/api/v1` needs a different shape (a path parameter wants `{ address }`), change the shared procedure instead of adding a v1-only twin: give it a `z.preprocess` input that maps the old shape onto the new one (`addressOrBareInputSchema` in `schemas/common/address.ts`, `profileListsInputSchema` in `schemas/list.ts`), move the web callers to the new shape, and mount it in `openApiRouter` (`routers/index.ts`). Map a legacy key only when the new key is absent, so it cannot become a query-string override on `/api/v1`. A query string carries only strings: a number input there is `z.coerce.number`, a boolean `queryBoolean`, a list `queryArray`, and a nested object (the feed cursor) `queryJson`, all in `schemas/common/query.ts`, each still accepting what `/rpc` sends. In `openApiRouter`, mount a router whole when every procedure in it is a public read; pick procedures by name only when it also holds writes.

## Staff procedures

`moderator` (`orpc.ts`) answers NOT_FOUND to everyone who is not staff, signed out included; `adminOnly` (`moderator.use`) adds FORBIDDEN for a moderator. The `admin` router (`routers/admin.ts`: the banner feed and removal, collection colours and Refresh collection list, and the Trade tracking and Message totals reads) is mounted on `/rpc` only, never `/api/v1`.

## Staff totals

Trade tracking and Message totals (`services/moderation/trade-tracking.ts`, `staff-trade.ts`, `message-totals.ts`) return counts, enums, ids, names, dates and hashes only, plus the staff trade's `collections` (indexer collection metadata, passed through as the console's attached trades pass it). Each query names its columns, and each procedure's `.output()` (`schemas/staff-totals.ts`) strips anything else, so no message body or card, offer note or caution, report note, excerpt or sanction reason reaches staff; a new field joins that schema as a type that cannot hold free text. Days are UTC: `rangeDays` and `rangeStart` (`lib/staff-totals.ts`) are computed once per read, from one `now`, so the SQL bound, the zero-filled days and the cache key's date agree. Fault in a failed trade is `faultSql` (`services/trade-fault.ts`), shared by the reputation's unfinished count and the repeat breakers, so the two never disagree. A pending wrong copy or request to cancel can outlive its trade, so every "still waiting" count gates on `trade.status = 'in_progress'`. Totals are cached 5 minutes under `mod:trade-totals:1:<days>:<utc-date>` and `mod:message-totals:1:<days>:<utc-date>`; bump the version when the stored shape changes. The attention list, the staff trade and tracker health are read live.

## Errors

A refusal the web app can show goes through `refuse(status, reason, message, data?)` (`src/lib/refuse.ts`): `reason` is a domain-prefixed code (`list_have_links_want`) from a `*_REFUSALS` tuple in `src/schemas/`, and `message` is an English sentence that the web app never renders; it serves tabs opened before a deploy and `/api/v1` callers. Chat, offer and moderation keep their own helpers with bare codes. A procedure that must keep an error code for old tabs to branch on declares it with `.errors()` and a `data: z.object({ reason })` schema. The web app translates the code through `refusalText` or the domain's own formatter, never `error.message`: a new `refuse()` code needs an `api_errors_*` string in `en`, `ko` and `ja`, and a new chat code a `chat_refused_*` string, worded in `features/chat/format.ts`.

## What every page loads

The web root loader awaits `config.getArtists` and `config.getFilterData` on every page, so either one failing takes the whole site down. Both read through `getStaleCache` (`services/redis.ts`): a stored copy is returned at once and refreshed in the background, so an outage of Cosmo or the indexer database, or a slow answer from either, serves the last good copy. A new read the root loader awaits goes through it too. A stored copy never expires, so when a value changes shape its key takes a version (`filter-data:2`), or the new code reads the old shape until the next refresh. `getArtists` also refuses to store a Cosmo answer missing any of `validArtists`, and with nothing stored falls back to `data/artists.json`, a snapshot to refresh by hand from the `value` of `artists:last-good` in Redis when Cosmo adds a member.

## Cosmo links

Every link change goes through `services/account/cosmo-link.ts` (user link and unlink) or `services/moderation/links.ts` (staff move and unlink), so `address_link_event` stays whole; a bare `UPDATE user_address` loses history and the relink cooldown (`COOLDOWN_DAYS` in `lib/link-rules.ts`, switched off at 0 since 2026-11-10; restoring 7 brings it back, and `link-rules.test.ts` switches to the 7-day tests by itself; restore the unlink dialogs' wording with it). Every writer takes locks in one order: `"user"` rows by id (`FOR SHARE` to read sanctions, `FOR NO KEY UPDATE` to write one; `FOR UPDATE` would also block the `KEY SHARE` of a notification insert for that user, and deadlock against an accept holding an offer row the writer cancels), then `pg_advisory_xact_lock(hashtext(lower(address)))` in address order, then reads, writes and the history insert in one transaction. A sanction write (`applyModAction` for every action but dismiss) locks the user row first, before the `user_sanction` insert, whose foreign-key check takes only `KEY SHARE`. `acceptOffer` takes both parties' user rows and addresses before the conversation lock and re-reads their links, so no unlink lands between its address read and the legs' snapshot; `anonymizeUser` locks its user row before cancelling offers, so the two never wait on each other in opposite orders. The refusal rules are pure, in `lib/link-rules.ts`. The link refusal codes live in `COSMO_LINK_REFUSALS`, the move and staff-unlink ones in `MODERATION_REFUSALS` (`services/moderation/core.ts`).

Every write that changes `user_address.user_id` (link, unlink, staff move and unlink, the account scrub) sets `is_default = false`; `user_address_default_linked` refuses a flag on an unlinked row, and `cosmoLink.setDefault` clears the account's flag before setting the new one, so `user_address_default_idx` keeps one per account.

A block (`blockUser`, and the report's also-block) locks both users' rows `FOR NO KEY UPDATE` in id order through `lockUsersForWrite` before the `user_block` insert, so an offer create or accept, which re-reads blocks after `lockParties`' `FOR SHARE`, either sees the block or finished first; it then cancels offers inside the same transaction, the same order a sanction write takes.

## Privacy and Trade

Profiles are public: holdings, serials, transfers and nicknames show to every viewer, as they are on chain. A list on Trade, or a discoverable list, shows its owner and its entries. The only per-list privacy left is `lists.hide_serial`, which shows that list's copies as counts (any copy), never by objekt id or serial. `user_address.private_profile`, `private_serial`, `hide_transfer` and `hide_nickname` are retired: nothing reads or writes them and `schema.ts` lacks them, but the columns stay in the database until the owner approves their drop migration.

A profile's bio (`user_address.bio`) reaches only the profile page and its owner's edit dialog: `toProfilePage` adds it while the profile shows its account, and `toPublicProfile` never carries it, so the hover card, linked previews and `/api/v1` don't. `profile.edit` keeps the stored bio when `bio` is absent (a tab from before it), and `normalizeUserText` (`schemas/common/user-text.ts`, tested) is the one cleanup (see Lists in `docs/lists.md` for what it keeps). Every write that takes an address off an account clears it (`unlink`, both branches of the staff move and unlink in `services/moderation/links.ts`, and `anonymizeUser`), so a bio never shows under an account that did not write it; a new writer of `user_address.user_id` sets `bio: null` too. The banner still stays on an unlinked row.

## Presence

`presence.online` is the only way presence leaves the server. `onlineAmong` (`services/presence.ts`) reads each asked id's switch and blocks, and the pure, tested `presenceTargets` (`lib/presence.ts`) drops the viewer's own id, any id with a block either way and anyone with `user.show_online` off. The viewer's own switch hides only them: with it off they still see others, as Discord's Invisible does. It reads the rest as `presence_stats` on each `user:#<id>` channel in one `/api/batch` (`presenceStatsRequest` and `onlineFromReplies`), sent with `parallel: true` because staging and production keep presence in Valkey, through `query()` (`realtime.ts`), the one Centrifugo call that returns its reply: one attempt, `null` when unset, slow or non-2xx. Presence fails closed: `null`, an error reply (the `user` namespace without `presence` answers code 108) or a missing reply reads as offline, so a down or unrestarted Centrifugo shows no dots. The rule is `showsOnlineTo`, apart from chat's `showsActivityTo`, which is both ways and has a request rule; Trade rows show the dot to any signed-in viewer.

Idle is a kind of online: `presence.online` returns `idle`, the online ids whose last activity in any tab was 10 or more minutes ago, beside `online`. `presence.active` (one call a minute at most from each active tab, `refuseOverUserLimit("presence-active", …, 10, 60)`) sets `presence:active:<id>` (`activeKey`) in Valkey to the current time in milliseconds, for `ACTIVE_MARK_SECONDS` (7 days), whatever the switch says. Reports come at most once a minute (`ACTIVE_REPORT_SECONDS` in `schemas/presence.ts`, which the web's reporter throttles by), so idle shows 10 to 11 minutes after the last activity. `onlineAmong` reads the marks with one `MGET` only for ids already online, so it never reads a hidden person's, and the pure, tested `idleFrom` (`lib/presence.ts`) turns them into idle ids. Idle fails toward online: a missing mark (a tab from before the reporter, or marks lost with Valkey) is not idle, an unreadable Valkey (`redisFailOpen` gives `null`) makes `idle` empty, and a failed mark is ignored. `idle` is always a subset of `online`; a tab from before it ignores the field and shows an idle person green.

## Account deletion

The `user` row is never deleted; deletion scrubs it in `anonymizeUser` (`services/account/anonymize.ts`). Both Better Auth paths end there: `beforeDelete` for a user deleting their own account, and the `user.delete.before` database hook, which returns `false`, for an admin's removal. A new foreign key to `user` may keep `onDelete: "cascade"`, but nothing may rely on the cascade firing.

What blocks deletion is decided once, in `lib/account-deletion.ts`. The `/delete-user` hooks, `user.deletionCheck` and `user.deletionToken`, and the scrub's re-check inside its transaction all call it through `deletionState`. Offer create and accept read both users `FOR SHARE` (`lockParties`) before writing, and refuse a deleted party. The scrub holds the row `FOR NO KEY UPDATE`, which waits for those reads while still letting a notification insert's foreign-key `FOR KEY SHARE` through.

`DELETE_REFUSALS` are bare codes, the one exception to the domain prefix, because Better Auth's `error.code` and `/account/danger?refused=` carry them too. A refusal after the emailed link spent its token reaches the browser through the after-hook in `services/account/auth.ts`, which returns a 302 `Response`. A thrown `ctx.redirect` there keeps the endpoint's error status, and browsers don't follow a `Location` on an error status.

## Market floor and price history

The rules for which listings count and what a price is in USD live once, in `services/market/aggregate.ts` (`countedListings`, `pricedUsd`, `usdPriceExpr`). Every market read (`market.summary`, `stats`, both listings reads) and the hourly price snapshot use them, so a change to which listings count lands there. `market.summary` reads through `getMarketSummary` (`services/market/summary.ts`), kept apart from `market/aggregate.ts` because the worker imports that module and must stay clear of `services/redis`: one Redis copy (`market:summary:2`, fresh 60 s, kept 15 min) is served stale past 60 s and refreshed in the background under a `SET NX` claim, and each process also serves its own copy while fresh. The copy carries the `market:v` it was built under and is never served under another, so a ban or trade block still drops it at once; bump the key when the stored value changes shape. `market.stats` and `market.priceHistory` are on `/api/v1`, so their outputs are public. `schemas/price-history.ts` holds the pure history helpers (cron, ranges, cache TTL, `floorChange`): the web build denies any client import of `packages/api/src` outside `schemas/` and `constants.ts` (`apps/web/vite.config.ts`), so a pure module the web needs lives there and imports nothing from `lib/`.

## Spin outcomes

A spin row of `activity.feed` and `transfers.byAddress` carries `spin` (`reward`, `broke` or `pending`, plus the reward), and the mint that rewarded it carries `rewardOf`, both added by `withSpinRewards` (`services/activity/spin-rewards.ts`) after the page is read. Rows are never dropped: folding a reward into its spin row is the web's choice, so `/api/v1`, the cursor and the Mint filter keep every row. The pairing rule lives once, in the pure `@repo/lib/spin-pairing` (tested), which the web's live feed runs too. `pending` turns `broke` against the newest indexed transfer, never the wall clock, so a lagging indexer leaves spins pending. The windowed read runs in its own transaction with `SET LOCAL jit = off`: the planner costs each window as a long scan and JIT-compiles the plan, which took 50 to 120 ms on prod against about 11 ms of reading.

## Objekt shapes

`mapOwnedObjekt` and `overrideCollection` live in `@repo/lib/server/objekt`. Run any `ValidObjekt` through `overrideCollection`: it applies the band-image rules and lists the fields an objekt carries. Colours come straight from the row, staff colours included: `setCollectionColors` (`services/admin/collections.ts`) writes them onto the indexer's `collection` row, so no read touches the app database for them (`packages/db/AGENTS.md`, Collection colours). A save runs in one indexer transaction: `lockColourRow` (`@repo/lib/server/collection-colours`, env-free, shared with the worker's replay), the pure `planColourWrite` (`@repo/lib/collection-colours`, tested), the UPDATE, then the `collection_override` audit entry inserted and committed in its own app transaction before the indexer commits, so a stored colour always has the history the replay reads; a failed audit stores nothing. After both commits it bumps the list and deletes Spin's `held-by:v3` entry (`forgetSpinHeld`, `services/objekt/owned.ts`), whose cached rows carry colours. `bumpCollectionList` (`services/objekt/collection.ts`, over the tested `lib/collection-bump.ts`) writes `collection:modified-at`, as does the worker's `process-collection-images` and replay script; it writes at least a second past the stored value, since Last-Modified is floored to the second and an UPDATE moves neither it nor the newest `created_at`. An `OwnedObjekt` at runtime:

- `id` is the objekt's token id; `mapOwnedObjekt` overwrites the collection's UUID with it.
- `collectionId` is the collection's `collection_id` string (`"201z"`-style), never the UUID.
- `receivedAt` and `mintedAt` are `Date`s on the server and ISO strings once serialised.
- `isPin` and `isLocked` are `undefined` when they do not apply.
