# @repo/api

oRPC routers (`src/routers/`), Zod inputs (`src/schemas/`), and the services they call (`src/services/`). Pure logic lives in `src/lib/` beside its `*.test.ts`.

## `/rpc` stays compatible with open tabs

A tab loaded before a deploy keeps calling `/rpc` with the input shape it was built with, so every input an older client sends must still validate to the same data. New input fields are optional with a default. Before changing an `.input()`, state what an open tab sends after the deploy and confirm it still validates.

When `/api/v1` needs a different shape (a path parameter wants `{ address }`), change the shared procedure instead of adding a v1-only twin: give it a `z.preprocess` input that maps the old shape onto the new one (`addressOrBareInputSchema` in `schemas/common/address.ts`, `profileListsInputSchema` in `schemas/list.ts`), move the web callers to the new shape, and mount it in `openApiRouter` (`routers/index.ts`). Map a legacy key only when the new key is absent, so it cannot become a query-string override on `/api/v1`. In `openApiRouter`, mount a router whole when every procedure in it is a public read; pick procedures by name only when it also holds writes.

## Errors

A refusal the web app can show goes through `refuse(status, reason, message, data?)` (`src/lib/refuse.ts`): `reason` is a domain-prefixed code (`list_have_links_want`) from a `*_REFUSALS` tuple in `src/schemas/`, and `message` is an English sentence that the web app never renders; it serves tabs opened before a deploy and `/api/v1` callers. Chat, offer and moderation keep their own helpers with bare codes. A procedure that must keep an error code for old tabs to branch on declares it with `.errors()` and a `data: z.object({ reason })` schema. The web app translates the code through `refusalText` or the domain's own formatter, never `error.message`; a new code needs an `api_errors_*` string in `en`, `ko` and `ja`.

## Lists

`writeList` (`services/list.ts`) is the one place a list row is created: `list.create` and `list.copy` both run `prepareList` first, outside any transaction (validation and partner reads use the pool, so a transaction waiting on them would hold a connection), then `writeList` inside theirs, which picks the profile slug on the transaction's own connection right before the insert. It returns the ids to `touchList` after commit. A copy's entries come from `planCopy` over the pure `lib/list-copy.ts`; it checks that the caller owns the target profile before it reads that profile's holdings from the indexer, so `list.copyPreview` cannot read another user's holdings. `copyMode`, `needsHoldings`, `carriesPrices` and `copyUnit` live in `schemas/list-copy.ts` because the web dialog imports them: it asks `copyPreview` for a count whenever the mode is not `rows`.

## Cosmo links

Every link change goes through `services/cosmo-link.ts` (user link and unlink) or `services/mod-links.ts` (staff move and unlink), so `address_link_event` stays whole; a bare `UPDATE user_address` loses history and the 7-day cooldown. Every writer takes locks in one order: `"user"` rows by id (`FOR SHARE` to read sanctions, `FOR NO KEY UPDATE` to write one; `FOR UPDATE` would also block the `KEY SHARE` of a notification insert for that user, and deadlock against an accept holding an offer row the writer cancels), then `pg_advisory_xact_lock(hashtext(lower(address)))` in address order, then reads, writes and the history insert in one transaction. A sanction write (`applyModAction` for every action but dismiss) locks the user row first, before the `user_sanction` insert, whose foreign-key check takes only `KEY SHARE`. `acceptOffer` takes both parties' user rows and addresses before the conversation lock and re-reads their links, so no unlink lands between its address read and the legs' snapshot; `anonymizeUser` locks its user row before cancelling offers, so the two never wait on each other in opposite orders. The refusal rules are pure, in `lib/link-rules.ts`. The link refusal codes live in `COSMO_LINK_REFUSALS`, the move and staff-unlink ones in `MODERATION_REFUSALS` (`services/moderation.ts`).

A block (`blockUser`, and the report's also-block) locks both users' rows `FOR NO KEY UPDATE` in id order through `lockUsersForWrite` before the `user_block` insert, so an offer create or accept, which re-reads blocks after `lockParties`' `FOR SHARE`, either sees the block or finished first; it then cancels offers inside the same transaction, the same order a sanction write takes.

## Privacy and Trade

Private stays private; Trade is the one surface a user opts into being public. A list on Trade, or a discoverable list, shows its owner and its entries on purpose. A `private_profile` address is answered for only to its owner (`isProfileHidden`, `services/privacy.ts`) in every read that could tie it to an account or its holdings: matching, the offer picker, chat targets, card holder checks. An exception is allowed only where the owner's own Trade list names the objekt. A `private_serial` address shows copies only as counts (any copy), never by objekt id or serial. `hide_user` is retired: list owners are shown, and the columns stay in the database until their drop migration.

## Account deletion

The `user` row is never deleted; deletion scrubs it in `anonymizeUser` (`services/account-anonymize.ts`). Both Better Auth paths end there: `beforeDelete` for a user deleting their own account, and the `user.delete.before` database hook, which returns `false`, for an admin's removal. A new foreign key to `user` may keep `onDelete: "cascade"`, but nothing may rely on the cascade firing.

What blocks deletion is decided once, in `lib/account-deletion.ts`. The `/delete-user` hooks, `user.deletionCheck` and `user.deletionToken`, and the scrub's re-check inside its transaction all call it through `deletionState`. Offer create and accept read both users `FOR SHARE` (`lockParties`) before writing, and refuse a deleted party. The scrub holds the row `FOR NO KEY UPDATE`, which waits for those reads while still letting a notification insert's foreign-key `FOR KEY SHARE` through.

`DELETE_REFUSALS` are bare codes, the one exception to the domain prefix, because Better Auth's `error.code` and `/account/danger?refused=` carry them too. A refusal after the emailed link spent its token reaches the browser through the after-hook in `services/auth.ts`, which returns a 302 `Response`. A thrown `ctx.redirect` there keeps the endpoint's error status, and browsers don't follow a `Location` on an error status.

## Chat: the first message is the start

`chat.start` only opens a conversation row and marks the caller's `conversation_member.opened_at`; it counts nothing and sends nothing. It also returns the thread's newest page (`loadThread`, `null` when that read fails) for the web to seed its cache with, so a Message click opens the thread in one request. It no longer returns `created`; no client read it. A conversation's first message or offer is its start: `appendMessage` runs the `first` callback (`openFirst`, `services/chat/start.ts`) under the row lock when `last_message_id` is null. `openFirst` re-runs `startVerdict` (Nobody, bans, blocks, mute, the start limit read from `conversation.started_by/started_at`) and stamps `started_by/started_at`. Any path that may append a first message takes `lockStarts` (the sender's advisory lock) before the conversation row lock, never after (`sendMessage`, `createOffer`, `checkStart`). `nextMemberState` puts the recipient of a card-less first message in Requests, whoever opened the conversation. An empty conversation opens as a thread only for a member with `created_by = me OR opened_at IS NOT NULL` (`visibleToMember`), and no conversation list shows it (`selectConversationRows` requires `last_message_id`), so a Message click that sends nothing leaves no row in anyone's inbox; the next click reuses it. `resolveCard` checks the listing and the holder through `cardAllowed`, and `hydrateCards` takes the viewer so a hide-serial list shows no serial or objekt id to anyone but its owner.

## Chat: requests and the icon's dot

Requests add no number to the Messages icon, but they set its dot: `hasUnseenRequests` (`services/chat/inbox.ts`, served as `chat.requestsUnseen`) is true while a request's `lastIncoming` message has an id above `message_pref.requests_seen_message_id`. `chat.seeRequests` moves that marker forward (`greatest`, computed in SQL at write time) when the web opens the Requests tab. Every `chat_message` event carries the viewer's `requestsUnseen`, so a new field on that event must be filled in `buildChatMessages` (`services/chat/live.ts`), beside `unread` and `requests`.

## Chat cards

A message holds an objekt card or a post card (a Trade post, by its list). An objekt card is stored as it always was, with no `kind`, so search on `card->>'collectionSlug'` keeps working; a post card is `{ kind: "post", listId, match? }`. `storedCardSchema` is the union, used only by `parseCard` and the writers of `message.card`. Every output an open tab reads keeps `storedObjektCardSchema`, so a post card there is `null`: `ChatMessage.card`, `ConversationRow.last.card` and `context`, the report excerpt's `card`, and offer items. A post card travels in new fields: `ChatMessage.post`, `ConversationRow.contextPost` and `last.post`, `postCard` beside `card` in the `chat.start` result, and the excerpt's optional `post: { listId }`. The new fields default to none, so a realtime event from a server that predates them still parses. A new reader of `message.card` chooses its schema on purpose.

`resolveCard` accepts a post card for a list the partner owns that is shown on Trade and not trade-sanctioned. With `withMatch` it saves the match from `personDetail`: the owner's collections on the sender's wants, then the sender's on the owner's, each as a count and the first three slugs in the person sheet's order. The client only asks. `fetchPostCards` (`services/trade-feed/`) reads the post live: either half of a have and want pair names the post that holds it now, a list gone or off Trade reads as removed, and a saved match stays as saved. Post cards and matches name collections, never serials.

## Offer get sources

A get item comes from the partner's lists while they have any (`partnerHasLists`), and `createOffer` checks nothing else. A target list that is have or sale on Trade (`Addressed.onlyList`, set in `resolveAddressed`) scopes the get side to that one list: `allowedEntries` narrows to it, and `keptGives` skips kept counter items. Since that list is itself one of the partner's lists, the collection fallback never applies. A want list target is unscoped. `offer.candidates` reports the scope as `scopedList`. `fromList` narrows the theirs picker through `allowedEntries` (and skips kept counter items, which sit on no list); the scope wins over it, and the send check is unchanged. The whole theirs list (`offer.candidates` without an offset) adds the partner's have and sale lists as `lists` (`partnerListChoices`) for the web's From choice, empty when scoped; `suggestOffer` skips that query. With none, the get side may draw on what the partner holds at visible addresses (profile not private): a specific objekt only at one that shows serials, any copy only at one that hides them, counted there, the same set the picker offers. `checkItems` counts that any copy over `getCopyHolders` (the hidden-serial addresses) but checks a named objekt against open any-copy legs over every copy holder (`held`), since those legs may draw on any address. `refusedCollectionAsks` (`services/offer/collection.ts`) checks this at send, with `collectionAskAllowed` as the pure rule; the `theirs-collection` candidates side (`theirCollectionPage`) refuses `not_listed` for a partner who has lists, so a stale tab can't bypass them. A collection item keeps `list_id` null, as a kept counter item does.

## Notification objekts

`writeNotes` (`services/offer/notes.ts`) fills `objekts` on every offer and trade note, in one read of the offers' creators and items, ordered by `noteObjekts` (`schemas/offer.ts`): what the reader gets first, three at most. A row written before it has none and the bell keeps its tile. `listNotifications` loads `collections` for `payload.objekts` as well as an alert's `latest`. The worker reaches it through `writeNotes`, and cards and payloads are `jsonb`: `apps/worker` and `packages/db` conventions are unchanged.

## Notification groups

`listNotifications` pages heads, not rows. An offer or trade row groups under its stored `group_key` (`offer:<conversationId>`, `trade:<tradeId>`); every other type keys on `row:<id>`. The SQL ranks each key's rows newest first, and only after that applies the cursor, the order and the limit to rank 1. So kind and retention filter before ranking, and an older row never becomes a head on a later page. A head carries `updates` (the rest of its group) and up to `EARLIER_LIMIT` `earlier` rows, attached by `attachEarlier` (`lib/notification-groups.ts`); both are absent when the row is alone. `writeNotes` upserts while a row is unread, so a group's only unread row is its head, and marking the head read reads the group. `partner.image` is never stored: the list fills it from `loadIdentities` beside the current name.

## Trade matching

Mutual is `mutualOf` in `schemas/trade.ts`: what the two can swap, the smaller of the swap counts (`tradeTheyHave`, `tradeYouHave`: have lists against want lists open to swaps). A sale list never counts toward it, though it counts toward the one-way counts (`theyHave`, `youHave`), so a person matched only through sale lists is One way. `candidates.ts` prefilters and orders Mutual on the same swap counts (`trade` in `matched`), before the ownership check. A want list's Open to is two booleans: Swaps only is `match_have` true and `match_sale` false, Swaps or buying both true, Buying only `match_have` false and `match_sale` true; `lists_open_to_something` keeps them from both being false, and `resolveOpenTo` (`schemas/open-to.ts`, beside `openToOf` and `flagsOf`, the one decode of the two booleans into Swaps only, Swaps or buying and Buying only; the Browse `CASE` in `trade-feed/query.ts` is its SQL twin) is what list create and edit save, so an old tab's edit that turns `matchSale` off restores swaps. A have list counts in a direction only against a want list open to swaps (`match_have`), a sale list only against one open to buying (`match_sale`), and `offerMatchesWantSql`, `candidates.ts`, `recount`, and Browse's `Viewer` indexes (`tradeWant`, `saleHave`) all apply it. A chip popover names only the lists that produced the match (`myListIds`). Ranking, Mutual only and the web chip all read it. Browse's per-person chip reads For you's pipeline through `personMatches` (`services/trade-matches/person.ts`, over `recountPartners`), so a change to the matching rules lands in one place. Browse's Mutual reads the Mutual people through `getMutualPeople` (`services/trade-matches/mutual.ts`, over `mutualPeople` in `lib/trade-rank.ts`): no 50-person slice and no idle tier, unlike `trade.forYou`. It pages by person, never by offset: through `resumeRanking` (`lib/trade-rank.ts`): with a loaded snapshot holding the cursor's person, in the order it saw, so a person who moved up between loads is still listed; otherwise (no snapshot, expired, or the person not in it) by rank through `peopleAfter`. The read loops are `readBatches` (`lib/trade-feed.ts`), tested there. Mutual only keeps a snapshot for that order too. Both feed rankings recount up to `FEED_CANDIDATE_LIMIT` (1000) candidates, cut in SQL by the ranking's own order (`fetchTradeCandidates`' `order`) before the ownership check; `trade.forYou` and `personMatches` keep `CANDIDATE_LIMIT` and the filter's order, which for `all` is the swap score first, as `rankPartners` ranks. For you's Any pages three phases (`feedPlan` and `fillPage`, `lib/trade-feed.ts`; `readPhase` in `services/trade-feed/index.ts`): `mutual` (the Mutual path, WTT only, skipped for WTB and WTS), then `oneWay` people ranked by the sum of both counts (`getOneWayPeople`, `services/trade-matches/one-way.ts`, cache key `trade:oneway-people:3`, over `recountPartners(…, "all", { order: "sum" })`, paged by `peopleAfter` with a `OneWayRank`), then the bump-ordered `tail`. `phaseScope` says what a phase leaves out: `oneWay` and the tail skip a Mutual person's WTT posts, and the tail skips every One way person. A page that runs dry in a phase fills from the next in the same call, and each post carries `section`. The cursor's optional `phase` and `oneWay` say where a page stopped, and only the phase it names gets the cursor, so a phase entered by handoff starts at its top. A cursor with neither, from an open tab, reads as the plain bump order (`bump`, no exclusions), and one with only a `rank` as Mutual. The rankings are cached for 5 minutes and refresh separately, so a person can leave Mutual or the One way set between two loads; the cursor's `scope` names a Redis snapshot (`services/trade-feed/scope.ts`, `trade:feed-scope:1`, one hour) of the people earlier loads saw in each ranking, and `mergeSeen` unions it with the current rankings, so a post already shown is never listed again. An expired snapshot falls back to the current rankings. Every Redis read on this path goes through `redisFailOpen` (`services/redis.ts`), as `getCache` does, so an outage costs the cache, not the feed; while Redis is unreachable `getCache` keeps values in process (`LOCAL_MAX_ENTRIES`), so upstream calls still run once per TTL per process. Compare with narrows the viewer once through `narrowViewer` (`lib/trade-feed.ts`), so chips, rings and filters share it. `trade.forYou` and `listMatchCount` stay only for open tabs. `trade.people` is what the web reads: it pages by person (`PEOPLE_PAGE_SIZE` 12, each row up to `PERSON_POST_LIMIT` posts, `peopleFeed` in `services/trade-feed/index.ts`) over the same phases, with a `(bumpedAt, userId)` cursor and `person` leading the first page (`lead` in the cursor keeps it out of later ones). A request makes each phase's first stage-2 read and at most `EXTRA_PEOPLE_READS` more (`readBudget`, `lib/trade-feed.ts`), so sold-out people can't chain recounts; a phase's cursor names the last person it read, kept or emptied, so a short or empty page still moves on. `peopleScope` leaves out every listed Mutual person from One way and the tail; a Mutual-ranked person with no kept WTT post is not in the Mutual section, so the later phases still list them. `trade.browse` keeps the post-paged `phaseScope` and `excludeWttOf` for open tabs. Matching candidates (`candidates.ts`) count only lists inside a listed post, so an idle list counts toward nobody; the viewer's own lists count whether listed or not. The For you cache key carries a version (`trade:foryou:8:`); bump it when the cached value changes shape or meaning, as `trade:mutual-people:6`, `trade:mutual-count:6`, `trade:person:5` and `trade:oneway-people:3` are.

## Wrong copies

A wrong copy is accepted in one place: `acceptCopy` (`services/trade-verify.ts`), under the trade's row lock. The receiver's Accept (`acceptSubstitute`, `auto: false`) and the worker's deadline, expiry and break (`auto: true`, which sets `auto_accepted`) all call it, and `finishSettle` ends the trade either way. It lives in `trade-verify.ts` because the worker can import that module and not `services/offer/substitute.ts`, whose chain reaches `env.ts`.

## Market floor and price history

The rules for which listings count and what a price is in USD live once, in `services/market-aggregate.ts` (`countedListings`, `pricedUsd`, `usdPriceExpr`). Every market read (`market.summary`, `stats`, both listings reads) and the hourly price snapshot use them, so a change to which listings count lands there. `market.stats` is on `/api/v1`, so its output is public; `market.priceHistory` is `/rpc` only and stays out of `openApiRouter`. `schemas/price-history.ts` holds the pure history helpers (cron, ranges, cache TTL, `floorChange`): the web build denies any client import of `packages/api/src` outside `schemas/` and `constants.ts` (`apps/web/vite.config.ts`), so a pure module the web needs lives there and imports nothing from `lib/`.

## Objekt shapes

`mapOwnedObjekt` and `overrideCollection` live in `@repo/lib/server/objekt`. Run any `ValidObjekt` through `overrideCollection`: it applies the colour and band-image overrides by slug. An `OwnedObjekt` at runtime:

- `id` is the objekt's token id; `mapOwnedObjekt` overwrites the collection's UUID with it.
- `collectionId` is the collection's `collection_id` string (`"201z"`-style), never the UUID.
- `receivedAt` and `mintedAt` are `Date`s on the server and ISO strings once serialised.
- `isPin` and `isLocked` are `undefined` when they do not apply.
