# @repo/api

oRPC routers (`src/routers/`), Zod inputs (`src/schemas/`), and the services they call (`src/services/`). Pure logic lives in `src/lib/` beside its `*.test.ts`.

## `/rpc` stays compatible with open tabs

A tab loaded before a deploy keeps calling `/rpc` with the input shape it was built with, so every input an older client sends must still validate to the same data. New input fields are optional with a default. Before changing an `.input()`, state what an open tab sends after the deploy and confirm it still validates.

When `/api/v1` needs a different shape (a path parameter wants `{ address }`), change the shared procedure instead of adding a v1-only twin: give it a `z.preprocess` input that maps the old shape onto the new one (`addressOrBareInputSchema` in `schemas/common/address.ts`, `profileListsInputSchema` in `schemas/list.ts`), move the web callers to the new shape, and mount it in `openApiRouter` (`routers/index.ts`). Map a legacy key only when the new key is absent, so it cannot become a query-string override on `/api/v1`. A query string carries only strings: a number input there is `z.coerce.number`, a boolean `queryBoolean`, a list `queryArray`, and a nested object (the feed cursor) `queryJson`, all in `schemas/common/query.ts`, each still accepting what `/rpc` sends. In `openApiRouter`, mount a router whole when every procedure in it is a public read; pick procedures by name only when it also holds writes.

## Errors

A refusal the web app can show goes through `refuse(status, reason, message, data?)` (`src/lib/refuse.ts`): `reason` is a domain-prefixed code (`list_have_links_want`) from a `*_REFUSALS` tuple in `src/schemas/`, and `message` is an English sentence that the web app never renders; it serves tabs opened before a deploy and `/api/v1` callers. Chat, offer and moderation keep their own helpers with bare codes. A procedure that must keep an error code for old tabs to branch on declares it with `.errors()` and a `data: z.object({ reason })` schema. The web app translates the code through `refusalText` or the domain's own formatter, never `error.message`: a new `refuse()` code needs an `api_errors_*` string in `en`, `ko` and `ja`, and a new chat code a `chat_refused_*` string, worded in `features/chat/format.ts`.

## What every page loads

The web root loader awaits `config.getArtists` and `config.getFilterData` on every page, so either one failing takes the whole site down. Both read through `getStaleCache` (`services/redis.ts`): a stored copy is returned at once and refreshed in the background, so an outage of Cosmo or the indexer database, or a slow answer from either, serves the last good copy. A new read the root loader awaits goes through it too. A stored copy never expires, so when a value changes shape its key takes a version (`filter-data:2`), or the new code reads the old shape until the next refresh. `getArtists` also refuses to store a Cosmo answer missing any of `validArtists`, and with nothing stored falls back to `data/artists.json`, a snapshot to refresh by hand from the `value` of `artists:last-good` in Redis when Cosmo adds a member.

## Lists

`writeList` (`services/list.ts`) is the one place a list row is created: `list.create` and `list.copy` both run `prepareList` first, outside any transaction (validation and partner reads use the pool, so a transaction waiting on them would hold a connection), then `writeList` inside theirs, which picks the profile slug on the transaction's own connection right before the insert. It returns the ids to `touchList` after commit. A copy's entries come from `planCopy` over the pure `lib/list-copy.ts`; it checks that the caller owns the target profile before it reads that profile's holdings from the indexer, so `list.copyPreview` cannot read another user's holdings. `copyMode`, `needsHoldings`, `carriesPrices` and `copyUnit` live in `schemas/list-copy.ts` because the web dialog imports them: it asks `copyPreview` for a count whenever the mode is not `rows`. `list.slugPreview` fills the edit form's URL field with the `generateProfileSlug` call `list.edit` makes, so a change to how a profile slug is made lands in one place; `profileSlugBase` lives in `lib/profile-slug.ts`, not `schemas/list.ts`, because `slugify` is CommonJS and a `schemas/` file that imports it ships it to the browser even where nothing calls it.

## Want-list rules

A rule (`list_rule`) is a definition plus ordinary want entries: each collection it wants is a `list_entries` row with `rule_id` set, so matching, Can swap, the feed and want alerts read them unchanged. The pure logic (`expandRule`, `ruleProblem`, `ruleLabel`, `ruleLine`) lives in `schemas/list-rule.ts` because the web imports it. Expansion is `services/list-rules/expand.ts`, env-free because the worker's `refresh-list-rules` imports it: `syncRuleEntries` locks the rule row and applies `ruleEntryDiff` (`lib/rule-entries.ts`, tested), inserting and deleting, never rebuilding, so entry ids survive and `want_alert_sent` keeps a wanted-again collection from alerting twice. Reads split rules from objekts: `fetchListWithEntries`, list previews, copy, remove, the Discord format and the trade chat card skip `rule_id` rows, and `list.rules` serves the strip. The feed folds a want side's rule entries into `rules` tiles (`ruleTiles`), and `Viewer.ruleWant` names the collections the viewer wants only through a rule, for For you's lines (`ruleMatchesOf`). A rule has no size limit (a set rule's class may be null, any class, so one artist alone reaches about 9,500 collections today); a list holds 20 rules.

## Cosmo links

Every link change goes through `services/cosmo-link.ts` (user link and unlink) or `services/mod-links.ts` (staff move and unlink), so `address_link_event` stays whole; a bare `UPDATE user_address` loses history and the 7-day cooldown. Every writer takes locks in one order: `"user"` rows by id (`FOR SHARE` to read sanctions, `FOR NO KEY UPDATE` to write one; `FOR UPDATE` would also block the `KEY SHARE` of a notification insert for that user, and deadlock against an accept holding an offer row the writer cancels), then `pg_advisory_xact_lock(hashtext(lower(address)))` in address order, then reads, writes and the history insert in one transaction. A sanction write (`applyModAction` for every action but dismiss) locks the user row first, before the `user_sanction` insert, whose foreign-key check takes only `KEY SHARE`. `acceptOffer` takes both parties' user rows and addresses before the conversation lock and re-reads their links, so no unlink lands between its address read and the legs' snapshot; `anonymizeUser` locks its user row before cancelling offers, so the two never wait on each other in opposite orders. The refusal rules are pure, in `lib/link-rules.ts`. The link refusal codes live in `COSMO_LINK_REFUSALS`, the move and staff-unlink ones in `MODERATION_REFUSALS` (`services/moderation.ts`).

Every write that changes `user_address.user_id` (link, unlink, staff move and unlink, the account scrub) sets `is_default = false`; `user_address_default_linked` refuses a flag on an unlinked row, and `cosmoLink.setDefault` clears the account's flag before setting the new one, so `user_address_default_idx` keeps one per account.

A block (`blockUser`, and the report's also-block) locks both users' rows `FOR NO KEY UPDATE` in id order through `lockUsersForWrite` before the `user_block` insert, so an offer create or accept, which re-reads blocks after `lockParties`' `FOR SHARE`, either sees the block or finished first; it then cancels offers inside the same transaction, the same order a sanction write takes.

## Privacy and Trade

Profiles are public: holdings, serials, transfers and nicknames show to every viewer, as they are on chain. A list on Trade, or a discoverable list, shows its owner and its entries. The only per-list privacy left is `lists.hide_serial`, which shows that list's copies as counts (any copy), never by objekt id or serial. `hide_user`, and `user_address.private_profile`, `private_serial`, `hide_transfer` and `hide_nickname`, are retired: nothing reads or writes them, and the columns stay in the database until their drop migration.

## Presence

`presence.online` is the only way presence leaves the server. `onlineAmong` (`services/presence.ts`) reads each asked id's switch and blocks, and the pure, tested `presenceTargets` (`lib/presence.ts`) drops the viewer's own id, any id with a block either way and anyone with `user.show_online` off. The viewer's own switch hides only them: with it off they still see others, as Discord's Invisible does. It reads the rest as `presence_stats` on each `user:#<id>` channel in one `/api/batch` (`presenceStatsRequest` and `onlineFromReplies`), sent with `parallel: true` because staging and production keep presence in Valkey, through `query()` (`realtime.ts`), the one Centrifugo call that returns its reply: one attempt, `null` when unset, slow or non-2xx. Presence fails closed: `null`, an error reply (the `user` namespace without `presence` answers code 108) or a missing reply reads as offline, so a down or unrestarted Centrifugo shows no dots. The rule is `showsOnlineTo`, apart from chat's `showsActivityTo`, which is both ways and has a request rule; Trade rows show the dot to any signed-in viewer.

Idle is a kind of online: `presence.online` returns `idle`, the online ids whose last activity in any tab was 10 or more minutes ago, beside `online`. `presence.active` (one call a minute at most from each active tab, `refuseOverUserLimit("presence-active", …, 10, 60)`) sets `presence:active:<id>` (`activeKey`) in Valkey to the current time in milliseconds, for `ACTIVE_MARK_SECONDS` (7 days), whatever the switch says. Reports come at most once a minute (`ACTIVE_REPORT_SECONDS` in `schemas/presence.ts`, which the web's reporter throttles by), so idle shows 10 to 11 minutes after the last activity. `onlineAmong` reads the marks with one `MGET` only for ids already online, so it never reads a hidden person's, and the pure, tested `idleFrom` (`lib/presence.ts`) turns them into idle ids. Idle fails toward online: a missing mark (a tab from before the reporter, or marks lost with Valkey) is not idle, an unreadable Valkey (`redisFailOpen` gives `null`) makes `idle` empty, and a failed mark is ignored. `idle` is always a subset of `online`; a tab from before it ignores the field and shows an idle person green.

## Account deletion

The `user` row is never deleted; deletion scrubs it in `anonymizeUser` (`services/account-anonymize.ts`). Both Better Auth paths end there: `beforeDelete` for a user deleting their own account, and the `user.delete.before` database hook, which returns `false`, for an admin's removal. A new foreign key to `user` may keep `onDelete: "cascade"`, but nothing may rely on the cascade firing.

What blocks deletion is decided once, in `lib/account-deletion.ts`. The `/delete-user` hooks, `user.deletionCheck` and `user.deletionToken`, and the scrub's re-check inside its transaction all call it through `deletionState`. Offer create and accept read both users `FOR SHARE` (`lockParties`) before writing, and refuse a deleted party. The scrub holds the row `FOR NO KEY UPDATE`, which waits for those reads while still letting a notification insert's foreign-key `FOR KEY SHARE` through.

`DELETE_REFUSALS` are bare codes, the one exception to the domain prefix, because Better Auth's `error.code` and `/account/danger?refused=` carry them too. A refusal after the emailed link spent its token reaches the browser through the after-hook in `services/auth.ts`, which returns a 302 `Response`. A thrown `ctx.redirect` there keeps the endpoint's error status, and browsers don't follow a `Location` on an error status.

## Chat: the first message is the start

`chat.start` only opens a conversation row and marks the caller's `conversation_member.opened_at`; it counts nothing and sends nothing. It also returns the thread's newest page (`loadThread`, `null` when that read fails) for the web to seed its cache with, so a Message click opens the thread in one request. It no longer returns `created`; no client read it. A conversation's first message or offer is its start: `appendMessage` runs the `first` callback (`openFirst`, `services/chat/start.ts`) under the row lock when `last_message_id` is null. `openFirst` re-runs `startVerdict` (Nobody, bans, blocks, mute, the start limit read from `conversation.started_by/started_at`) and stamps `started_by/started_at`. Any path that may append a first message takes `lockStarts` (the sender's advisory lock) before the conversation row lock, never after (`sendMessage`, `createOffer`, `checkStart`). `nextMemberState` puts the recipient of a card-less first message in Requests, whoever opened the conversation. An empty conversation opens as a thread only for a member with `created_by = me OR opened_at IS NOT NULL` (`visibleToMember`), and no conversation list shows it (`selectConversationRows` requires `last_message_id`), so a Message click that sends nothing leaves no row in anyone's inbox; the next click reuses it. `resolveCard` checks the listing and the holder through `cardAllowed`, and `hydrateCards` takes the viewer so a hide-serial list shows no serial or objekt id to anyone but its owner.

## Chat: requests and the icon's dot

Requests add no number to the Messages icon, but they set its dot: `hasUnseenRequests` (`services/chat/inbox.ts`, served as `chat.requestsUnseen`) is true while a request's `lastIncoming` message has an id above `message_pref.requests_seen_message_id`. `chat.seeRequests` moves that marker forward (`greatest`, computed in SQL at write time) when the web opens the Requests tab. Every `chat_message` event carries the viewer's `requestsUnseen`, so a new field on that event must be filled in `buildChatMessages` (`services/chat/live.ts`), beside `unread` and `requests`.

## Chat: deals

A conversation's row and thread carry its `deal`: the most urgent of its open offer, running trades and trades still to rate, since one conversation can hold several at once. `readDeals` (`services/chat/deal.ts`) reads them for a page in one statement and runs `rateRefusal` itself; the pure `dealOf` (`schemas/chat-deal.ts`, tested) picks a Needs you state first, then any other live one, then one to rate, the newest offer winning a tie, and decides a trade's state in the web's `stepKind` order. `needsYouSql` is the SQL twin of `NEEDS_YOU_STATES` and serves both `chat.list`'s `show: "needs-you"` and `chat.inboxCounts`, which leaves out muted conversations as the Messages icon does. `unreadCount` and `deal` are filled in `toConversationRows`, so the list, `loadConversationRow` and every `chat_message` event carry them; both have schema defaults, so an event from the previous build still parses.

## Chat: replies

`message.reply_to_id` names the message a reply answers: a bare id, checked by `sendMessage` to be a text or card message of the same conversation (`invalid_reply` otherwise). `ChatMessage.replyTo` is built at read time in `toChatMessages`, from one read of the quoted rows joined through each reply's own conversation, then the pure `quoteSourceOf` and `replyQuote` (`schemas/chat.ts`, tested), so a quote follows an unsend made after the reply and never carries unsent text or card; a missing row reads as unavailable. Every `MessageRow` source (`loadThread`, `appendMessage`'s return, `findSentMessage`) selects `reply_to_id`, or that path's messages lose their quote.

## Chat cards

A message holds an objekt card or a post card (a Trade post, by its list). `message.card` stores either with its `kind`: `{ kind: "objekt", collectionSlug, objektId?, listId? }` or `{ kind: "post", listId, match? }`; search reads `card->>'collectionSlug'`. `storedCardSchema` is the union, read through `parseCard`. Every output carries a card with its `kind`: `ChatMessage.card` and `ConversationRow.context` are the objekt or post view, `ConversationRow.last.card` names the kind, and the `chat.start` result's `card` holds the input, view and collections of either. A card input names its `kind`. Offer and trade items are drawn as objekt cards through `hydrateCards`, which takes a `CardRef` (an objekt card without its `kind`). A report excerpt entry keeps its message's card the same way, a post card by its list only (`card: { kind: "post", listId }`), so it shows what was shared and not the match.

`resolveCard` accepts a post card for a list the partner owns that is shown on Trade and not trade-sanctioned. With `withMatch` it saves the match from `personDetail`: the owner's collections on the sender's wants, then the sender's on the owner's, each as a count and the first three slugs in the person sheet's order, and `canSwap` (`mutualOf` above zero), which the web's first-line suggestion reads; a card saved before it has none and reads as Can swap. The client only asks. `fetchPostCards` (`services/trade-feed/`) reads the post live: either half of a have and want pair names the post that holds it now, a list gone or off Trade reads as removed, and a saved match stays as saved. Post cards and matches name collections, never serials.

## Offer get sources

A get item comes from the partner's lists while they have any (`partnerHasLists`), and `createOffer` checks nothing else. Those lists are `askableOnTrade` (`services/trade-lists.ts`): have or sale, bound, and put on Trade, idle or not; a bound list kept off Trade is never asked from. Where an offer starts (a list target, a conversation) never narrows the get side. `fromList` narrows the theirs picker through `allowedEntries` (and skips kept counter items, which sit on no list); the send check is unchanged. The whole theirs list (`offer.candidates` without an offset) adds the partner's lists on Trade as `lists` (`partnerListChoices`) for the web's List choice; `suggestOffer` skips that query. With none, the get side may draw on what the partner holds at any linked address (`collectionAddresses`), by specific objekt only, since every copy there shows its serial: the same set the picker offers. `refusedCollectionAsks` (`services/offer/collection.ts`) checks this at send, with `collectionAskAllowed` as the pure rule; the `theirs-collection` candidates side (`theirCollectionPage`) refuses `not_listed` for a partner who has lists, so a stale tab can't bypass them. A collection item keeps `list_id` null, as a kept counter item does.

`suggestOffer` (`offer.suggest`) reads the person-row pipeline: `recountPartners` for the one partner under the row's Compare with sides, then fills by the rule the row's chip follows (`fillMatches`): with a Can swap person, opened without a post or from the person's post in the counted pair, the `swapPair` matches both ways, each cut to the pair's lists; otherwise only the side with more matches through the post (or all), You get on a tie, swaps and sales alike (no top-up is set for a sale). Near matches still skip every match through the post, the unfilled side's too. Each get item is matched back to its match's list entry by `matchEntry`, the rule sending uses (`itemsOnLists`), since the picker keeps one list per objekt and two lists can hold the same copy. It returns the picks `chooseMatchPicks` (`lib/offer-prefill.ts`) chooses and `matched` per side, the count before the side limit; with `post`, only that post's lists (`postSides`) and the post's name. The narrowing is pure, in `lib/offer-prefill.ts`, beside its tests.

## Notification objekts

`writeNotes` (`services/offer/notes.ts`) fills `objekts` on every offer and trade note, in one read of the offers' creators and items, ordered by `noteObjekts` (`schemas/offer.ts`): what the reader gets first, three at most. A row written before it has none and the bell keeps its tile. `listNotifications` loads `collections` for `payload.objekts` as well as an alert's `latest`. The worker reaches it through `writeNotes`, and cards and payloads are `jsonb`: `apps/worker` and `packages/db` conventions are unchanged.

## Notification prefs

`notifications.prefs` returns `{ enabled, match }`: `enabled` per type (a missing row takes `NOTIFICATION_DEFAULTS`), and `match` (`any` or `mutual`, a null or missing row reading as `ALERT_MATCH_DEFAULT`) for the two list alerts. `setPref` stays the boolean switch; `setAlertMatch` writes a list alert's Off, Any or Can swap in one upsert, and Off keeps the stored `match`. `recountPartners`, `resolveTradeSides` and `mutualPartnerIds` live in `services/trade-matches/recount.ts`, which the worker imports, so it must stay clear of `services/redis`; `index.ts` re-exports them.

## Notification groups

`listNotifications` pages heads, not rows. An offer or trade row groups under its stored `group_key` (`offer:<conversationId>`, `trade:<tradeId>`); every other type keys on `row:<id>`. The SQL ranks each key's rows newest first, and only after that applies the cursor, the order and the limit to rank 1. So kind and retention filter before ranking, and an older row never becomes a head on a later page. A head carries `updates` (the rest of its group) and up to `EARLIER_LIMIT` `earlier` rows, attached by `attachEarlier` (`lib/notification-groups.ts`); both are absent when the row is alone. `writeNotes` upserts while a row is unread, so a group's only unread row is its head, and marking the head read reads the group. `partner.image` is never stored: the list fills it from `loadIdentities` beside the current name.

## Trade matching

Mutual (Can swap) is `mutualOf` in `schemas/trade.ts`, which returns `counts.swap`: what the two can swap inside one post on each side. `swapScore` (`lib/trade-person.ts`, run by `matchCounts`) groups each swap match's `swapMyListIds` and `swapPartnerListIds` (the lists `trade` holds through, which `recount` fills; `myListIds` and `partnerListIds` also carry sale lists) by post pair and keeps the best pairing's smaller count, with that pairing's they-have count as `swapTheyHave` and the pairing as `swapPair` (the viewer's list ids in it and the person's post key, which is that feed post's `id`); the web's rules note (`swapThroughRules`) counts only rule matches inside it. A post key is the id of the pair's have or sale list: the viewer's come from `viewerPostOf` (`lib/trade-rank.ts`, over `pickedSides`, keyed only when the offering half swaps), carried on `Sides.postOf` by `resolveTradeSides`; the partner's from `partner_post` in `candidates.ts`, which pairs a listed list with its `linked_list_id` when that list is listed too, on the other side, and the offering half swaps. `recount` puts both maps on the partner as `posts`, so every `matchCounts(partner)` reads them. A list with no key counts one way only. The pooled swap counts (`tradeTheyHave`, `tradeYouHave`: lists offering swaps against want lists open to swaps, over all lists) are read by nothing now; they stay in the output only for tabs built before the web dropped its "No swap" chip, and can go in a later deploy. `candidates.ts` computes its own pooled swap counts in SQL for the Mutual prefilter and order, a superset of the per-post rule that the recount then narrows. A list offers swaps when it is a have list, or a sale list with `takes_swaps` (Sell or swap): one predicate, `offersSwapsSql` (`services/trade-lists.ts`) and its TS twin `offersSwaps` (`schemas/open-to.ts`), which `offerMatchesWantSql`, `candidates.ts`, the feed's `postsCte`, `TAG_WHERE` and match index, and the viewer's `tradeHave` all read. A Sell only sale list never counts toward Mutual, though it counts toward the one-way counts (`theyHave`, `youHave`), so a person matched only through such lists is One way. A candidate entry carries `swap` and `sale`, and a Sell or swap entry can be both; `recount` judges haves on `swap` (an entry cached before it reads `swap` as `!sale`) and sales on `sale`. A want list's Open to is two booleans: Swaps only is `match_have` true and `match_sale` false, Swaps or buying both true, Buying only `match_have` false and `match_sale` true; `lists_open_to_something` keeps them from both being false, and `resolveOpenTo` (`schemas/open-to.ts`, beside `openToOf` and `flagsOf`, the one decode of the two booleans into Swaps only, Swaps or buying and Buying only; the Browse `CASE` in `trade-feed/query.ts` is its SQL twin) is what list create saves; a want list's Open to after that is the post composer's. A want list linked to a have list is never Buying only: `pairRefusesOpenTo` (same module) is the rule, and `checkLinkedList` refuses it with `list_pair_buying_only` on list create (every pair refusal is decided by the pure `pairRefusal`, `lib/list-pair.ts`), reading the want side's Open to (the flags a want list is about to save, or a have list's partner's), so a WTT pair's want side always takes swaps. A have list counts in a direction only against a want list open to swaps (`match_have`), a sale list only against one open to buying (`match_sale`), and `offerMatchesWantSql`, `candidates.ts`, `recount`, and Browse's `Viewer` indexes (`tradeWant`, `saleHave`) all apply it. A chip popover names only the lists that produced the match (`myListIds`). Ranking, Mutual only and the web chip all read it. `trade.people`'s per-person chip reads the matching pipeline through `personMatches` (`services/trade-matches/person.ts`, over `recountPartners`), so a change to the matching rules lands in one place. Its Mutual reads the Mutual people through `getMutualPeople` (`services/trade-matches/mutual.ts`, over `mutualPeople` in `lib/trade-rank.ts`), and its One way the people ranked by the sum of both counts through `getOneWayPeople` (`services/trade-matches/one-way.ts`, over `recountPartners(…, "all", { order: "sum" })`): no slice and no idle tier. The read loops are `readBatches` (`lib/trade-feed.ts`), tested there. Both feed rankings recount up to `FEED_CANDIDATE_LIMIT` (1000) candidates, cut in SQL by the ranking's own order (`fetchTradeCandidates`' `order`) before the ownership check; `personMatches` keeps `CANDIDATE_LIMIT` and the filter's order, which for `all` is the swap score first, as `rankPartners` ranks. The rankings are cached for 5 minutes and refresh separately, so a person can leave Mutual or the One way set between two loads; the stored people order below keeps a scroll steady across that. Every Redis read on this path goes through `redisFailOpen` (`services/redis.ts`), as `getCache` does, so an outage costs the cache, not the feed; while Redis is unreachable `getCache` keeps values in process (`LOCAL_MAX_ENTRIES`), so upstream calls still run once per TTL per process. Compare with narrows the viewer once through `narrowViewer` (`lib/trade-feed.ts`), so chips, rings and filters share it. `trade.people` is what the web reads: it pages by person (`PEOPLE_PAGE_SIZE` 12, each row every post the feed keeps for that person, `peopleFeed` in `services/trade-feed/people.ts`) through a stored order. A first-page `person` skips the order and returns only that person's row, or none, with no cursor; `lead` in the cursor only serves cursors from before that. Page 1 builds the whole order (`buildOrder`; `buildPeopleOrder` in `lib/trade-feed.ts`): Browse by newest bump, Mutual only the Mutual people with a kept WTT post, Any those, then the One way people with a kept post, then everyone else by bump. A person keeps their first place, so a Mutual-ranked person with no kept WTT post lands in One way. It is stored for an hour (`savePeopleOrder`, `services/trade-feed/scope.ts`, `trade:people-order:3:<viewerId|anon>:<token>`, the token a hash of the order so a reload or every signed-out reader shares one key, bound to `ordersFingerprint` of the filters, mode, Compare with list and lead), and later pages read it by position (the cursor's `order` and `at`), so a ranking or a bump that changes mid-scroll moves no one; the rankings and kept-post checks run only when the order is built. A person whose posts all emptied is skipped where their place comes. Past `ORDER_LIMIT` (2000) the tail goes on by the `(bumpedAt, userId)` keyset from the order's `more`. When the order is gone or was built for other filters, the server builds it again and goes on by `resumeAt`: after the cursor's person, else at `at`. The cursor carries `bumpedAt` and `userId` for that and for the keyset past a capped order. A request makes its first stage-2 read and at most `EXTRA_PEOPLE_READS` more (`readBudget`, `lib/trade-feed.ts`), so sold-out people can't chain recounts; `at` moves past every person read, kept or emptied, so a short or empty page still moves on. The partner side of a match is `tradePartnerSql` and `listedCte` (`services/trade-lists.ts`, `services/trade-feed/query.ts`), shared with the worker's want-list alerts, so a partner rule changes there for both. Matching candidates (`candidates.ts`) count only lists inside a listed post, so an idle list counts toward nobody; the viewer's own lists count whether listed or not. A near match (a collection that would count if one side's Open to allowed it) comes only from the viewer index: `nearFor` (`lib/trade-feed.ts`) is set differences of the `Viewer` sets beside `indexFor`, so the two change together and a match is never near. It rides on the viewer's reads only (strip items and `side.near`, `trade.sideItems`, `trade.listMatches`, `offer.suggest`'s `near` through `personNear`, the picker's `tags` through `pickerTagsFor`) and never enters the recount, the rankings, their caches, alerts or chat cards. The ranking caches carry a version (`trade:mutual-people:9`, `trade:mutual-count:9`, `trade:oneway-people:5`, `trade:person:8`, `trade:people-order:3`); bump it when the cached value changes shape or meaning.

## Trade posts

A post is still its lists: `discoverable`, the link on both rows, a want list's Open to and a sale list's `takes_swaps`. There is no post table. A want list pairs with a have list, or with a sale list that takes swaps (`checkLinkedList` refuses a Sell only one with `list_sale_links_sell_only`); `groupPosts` and `postsCte` fold either kind of pair into one post, and a sale post with swaps is tagged WTS then WTT, then WTB when its want side is open to buying (a Sell post's "also pay", saved as the want list's `match_sale`, as on a Swap post). `schemas/trade-post.ts` is the one source of post kinds (Swap, Sell, Buy) and tags, pure and imported by the web: `tagsOf` (WTT for a have list or a want list open to swaps, WTB for a want side open to buying, WTS for a sale list; WTT before WTB, and a sale post leads with WTS), `postKindOf`, `groupPosts` (which `pairPosts` in `lib/trade-feed.ts` wraps), and `planPost`, which turns a composer choice into the writes or a `TRADE_POST_REFUSALS` code. `TAG_WHERE` in `services/trade-feed/query.ts` is the SQL twin of `tagsOf`: its `wtb` reads the pair partner's `partner_match_sale`/`partner_match_have` from `postsCte`, for a pair anchored on a have or a sale list, and its `wtt` reads no partner column, since `excludeWttOf` negates it. Feed posts and `trade.myPosts` carry `tags`; chat post cards carry `tag` only, the first tag. `trade.savePost` and `trade.takeDownPost` (`services/trade-post.ts`) lock the poster's have, want and sale rows `FOR UPDATE`, run `planPost` on them and write in one transaction, then `touchList` every changed id. A Swap post with one list, or a Sell post that takes swaps, keeps that list's pair; any other split of a pair needs `unpair`, except that a list an edit drops from the post is unlinked from the half that stays. Taking a post off Trade keeps its link. `list.edit` takes no Trade state for any list type: a list's link, Open to and `discoverable` belong to its post, which `trade.savePost` writes, and the `discoverable` a tab from before this rule still sends is stripped by the input schema.

## Wrong copies

A wrong copy is accepted in one place: `acceptCopy` (`services/trade-verify.ts`), under the trade's row lock. The receiver's Accept (`acceptSubstitute`, `auto: false`) and the worker's deadline, expiry and break (`auto: true`, which sets `auto_accepted`) all call it, and `finishSettle` ends the trade either way. It lives in `trade-verify.ts` because the worker can import that module and not `services/offer/substitute.ts`, whose chain reaches `env.ts`.

## Legs marked as received

The receiver can close a waiting leg by hand (`confirmLeg`, `services/offer/confirm.ts`), under the trade's row lock and through `finishSettle`, as Accept on a wrong copy does. The leg gets `open = false`, `verified_at` and `confirmed_at`, and no `tx_hash`, `verified_objekt_id` or `transfer_id`, so every "done" count that reads `verified_at` (progress, the cancel lock, `tradeOutcome`, the unfinished rule) takes it unchanged. A verified leg therefore may have no hash. Only three reads tell a confirmed leg apart, through `confirmed_at`: reputation's verified count (`done` skips any trade with one), `rateRefusal` (`confirmedLegs`, refusing `confirmed_trade` on a completed trade only, so a failed one keeps the deliverer's rating; every caller passes it, `readDeals` included) and the trade read's `confirmedAt`. A pending wrong copy on the leg refuses `copy_pending`: the copy is decided first, since the worker's copy jobs skip a closed leg and would leave it pending. The giver gets `leg_confirmed` unless the confirmation ends the trade, which sends `completed` to both instead. `finishSettle` marks any `completed` note `confirmed: true` when a leg of the trade was confirmed, whoever closed the last leg, and the popover offers no Leave feedback on it.

## Market floor and price history

The rules for which listings count and what a price is in USD live once, in `services/market-aggregate.ts` (`countedListings`, `pricedUsd`, `usdPriceExpr`). Every market read (`market.summary`, `stats`, both listings reads) and the hourly price snapshot use them, so a change to which listings count lands there. `market.summary` reads through `getMarketSummary` (`services/market-summary.ts`), kept apart from `market-aggregate.ts` because the worker imports that module and must stay clear of `services/redis`: one Redis copy (`market:summary:2`, fresh 60 s, kept 15 min) is served stale past 60 s and refreshed in the background under a `SET NX` claim, and each process also serves its own copy while fresh. The copy carries the `market:v` it was built under and is never served under another, so a ban or trade block still drops it at once; bump the key when the stored value changes shape. `market.stats` and `market.priceHistory` are on `/api/v1`, so their outputs are public. `schemas/price-history.ts` holds the pure history helpers (cron, ranges, cache TTL, `floorChange`): the web build denies any client import of `packages/api/src` outside `schemas/` and `constants.ts` (`apps/web/vite.config.ts`), so a pure module the web needs lives there and imports nothing from `lib/`.

## Objekt shapes

`mapOwnedObjekt` and `overrideCollection` live in `@repo/lib/server/objekt`. Run any `ValidObjekt` through `overrideCollection`: it applies the colour and band-image overrides by slug. An `OwnedObjekt` at runtime:

- `id` is the objekt's token id; `mapOwnedObjekt` overwrites the collection's UUID with it.
- `collectionId` is the collection's `collection_id` string (`"201z"`-style), never the UUID.
- `receivedAt` and `mintedAt` are `Date`s on the server and ISO strings once serialised.
- `isPin` and `isLocked` are `undefined` when they do not apply.
