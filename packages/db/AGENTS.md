# @repo/db

Two databases, two schemas:

- **App** (`DATABASE_URL`): `src/schema.ts`, `src/auth-schema.ts`, `src/relation.ts`; migrations in `migrations/` from `db:generate`.
- **Indexer** (`INDEXER_DATABASE_URL`): `src/indexer/` mirrors the tables `apps/indexer` owns. Read from this side, written by the indexer and the worker; the web's one write is staff colours on `collection` (Collection colours). Its Drizzle-owned changes are **hand-written SQL** in `indexer-migrations/`, applied by the indexer on start after the Subsquid migrations (`apps/indexer/src/migrate-drizzle.ts`). `drizzle-kit generate` against `drizzle-indexer.config.ts` would diff against tables the indexer owns, so write those folders by hand.

## Production

The root `.env` is production for both databases. `.env.local` points `DATABASE_URL` at the local compose Postgres and `INDEXER_DATABASE_URL` at production with `default_transaction_read_only=on`; there is no local indexer. The `guard-prod-db` hook blocks `db:migrate` / `db:push` unless `.env.local` points `DATABASE_URL` at a local host, and blocks indexer schema writes always: those the user runs.

## Migrations run before the deploy

Pending migrations run before the new code is live: on the VPS, `docker compose run --build --rm migrate` (`--build`, or a stale image applies an old migration set and still exits 0), then bring up web and worker. The `migrate` service sits behind a compose profile, so `up` never starts it. It connects directly, never through pgbouncer: to the compose `postgres` by default, or to `MIGRATE_DATABASE_URL` when set. So each migration must work with the code still running from `main`: **expand, deploy, then contract**. Add a column, deploy the code that uses it, and drop the old column in a later migration once nothing live reads it. Drizzle v1 runs every migration folder whose name is not recorded, in any order, without a hash check, so a migration written after a column already left `schema.ts` needs `drizzle-kit generate --custom` (a plain generate finds no diff). Make such drops `IF EXISTS`, since a local database may already lack the column.

A column can leave `schema.ts` before it leaves the database: generate the migration so its snapshot drops the column, then replace its SQL with a no-op (`20261024135516_retire_privacy_columns`). Otherwise the next `db:generate` writes the `DROP COLUMN` into whatever change comes next. `user_address.private_profile`, `private_serial`, `hide_transfer` and `hide_nickname` are kept that way, values intact, until the owner approves their drop. `user.multi_post_asks` is kept that way too (`NOT NULL DEFAULT true`, so Better Auth's insert of a user without it works), until a later migration drops it (`DROP COLUMN IF EXISTS`, with `lock_timeout`) once the build that stopped reading it is live.

## Trade posts

`trade_post` is one row per Trade post: `lead_list_id` (a have or sale list, or a Buy post's want list) and at most one `want_list_id`. Every read of a post's pairing outside a write path reads it, through `postPairsSql`, `postPartnerSql` and the `lists.postLed` / `postWanted` relations; writers write the rows too, through `writePosts` and the pure `planPostChange` (`packages/api/docs/trade.md`, Trade posts). The rows are the only place a pairing is stored. `lists.linked_list_id`, the link they replaced, left in two migrations, as Migrations run before the deploy asks: `20261115092944_retire_linked_list_id` (a no-op, with the build that stopped writing it) and `20261115125616_drop_linked_list_id` (the drop, once that build was live). No web or worker build from before `c66841be` can run against the database now. `20261114104128_trade_post_backfill` filled the table once, on an empty table, after a guard that fails the migration on any link that is not a mutual have-or-sale to want pair of one owner. Its ids start at 1,000,000, above any list id, and a row keeps its id while it stays one post, even when its lead changes (`packages/api/docs/trade.md`, Trade posts): a writer never deletes and re-creates a row for the same lists, so a row id can be stored as a post's address. Edit post keeps its row whichever of the post's lists it swaps or drops: the row takes the post's new lead, so the post keeps its id and its hides, and the list the row led keeps an off-Trade row of its own. `lead_list_id` still cascades, as the net under a delete that goes around `deleteList` (`anonymizeUser`). `offer.post_id` stores such a row id (`20261115164916_offer_post_id`): `ON DELETE SET NULL`, never CASCADE, which would delete offers with their items, messages and trades, and a partial index so a row delete does not scan `offer`. It names the post "Offer on" reads, and sits beside `offer.post_list_id`, the list that led it, which the line falls back to once the row is gone (`packages/api/docs/offers.md`). Offers the previous build created between that migration and its web deploy keep `post_id` NULL; `offer-reads-post-id`, the change that reads `post_id`, reconciles that window with a one-off, id-bound backfill run apart from its deploy (its task 7.4), and until then those offers read their line through `post_list_id`. Neither list column is unique, on purpose: one list may sit in more than one post later. The planner already holds a list in several rows; The readers take rows too (`packages/api/docs/trade.md`, Trade posts): only `planPost`'s refusal of a list in another post (`trade_post_list_in_post`) and drift check 2 keep production at one row per list, until `shared-lists`. Each row also holds its sides' Trade state and bumps (`lead_on_trade`, `lead_bumped_at`, `want_on_trade`, `want_bumped_at`) and the post's Open to and `takes_swaps`, written per row from the write (and by `bumpPerson`, for bumps), with `lists.discoverable` derived from the rows, and which the reads that build posts take from the row. Bumps live on the rows only: `lists.bumped_at` is gone (`packages/api/docs/trade.md`, Trade posts). They came in two migrations: `20261120072416_trade_post_state` added and backfilled them while the live build still wrote `lists` only, and `20261120085525_trade_post_state_reconcile` ran the backfill again under `LOCK TABLE lists IN EXCLUSIVE MODE` once the build that writes both (web A, `2f107ab3`) was live. **Since `trade_post_state_reconcile`, no web build older than `2f107ab3` may run**: it writes `lists` only, the rows go stale, and the feed reads them. Going lower needs a new reconcile migration first. The worker was exempt: it writes none of these columns, and read `lists`, which equalled the rows. A hide (`hidden_trade_post`) names a row: `post_id` references `trade_post(id)` `ON DELETE CASCADE`, and the primary key is `(user_id, post_id)`, so a hide ends with its row unless `writePosts` moved it first (`packages/api/docs/trade.md`, Partner rules, hidden and idle posts). Migration `hidden_trade_post_by_row` backfilled it, and added the repo's first trigger, `hidden_trade_post_fill_post_id`, which gave the hides of builds still writing only `list_id` (the list a hide was made on) their row. Drizzle's snapshot does not track triggers or their functions, so `db:generate` never shows or drops them: a migration that removes one drops it, and its function, by hand. `trade-post-state-contract` retired `lists.bumped_at` and `hidden_trade_post.list_id` in two migrations. `20261121094632_retire_contract_columns` removed `lists.bumped_at`, `hidden_trade_post.list_id` and `hidden_trade_post_list_id_idx` from `schema.ts` only, with the build that stopped using them (`8b05487c`), and rebuilt `lists_trade_discoverable_idx` as `lists (list_type) WHERE discoverable`, which the Marketplace and want alerts read through, in place of `lists_trade_feed_idx`. `20261121171021_drop_contract_columns` then dropped both columns (and with `list_id` its index), the trigger and its function, once web and the worker both ran that build or later. **No web or worker build older than `8b05487c` can run against the database now**: going lower needs a migration that re-adds both columns and refills `lists.bumped_at` from the rows first. Dropping a foreign key into `lists` takes ACCESS EXCLUSIVE on `lists`, so `hidden_trade_post_by_row` takes it first, with a 1 s `lock_timeout`, then `trade_post` and `hidden_trade_post` with `NOWAIT`: writers lock `lists` before rows and hides, but a read that names `hidden_trade_post` before `lists` (`fetchHiddenPosts`, the worker's `unhidePosts`) can hold it while queued behind the migration, so the migration fails and is rerun rather than deadlock. A later migration that touches those tables takes them the same way. `apps/worker/src/script/trade-post-drift.ts` checks the rows against `lists`, read-only (check 5 each list's `discoverable` against its rows, check 6 each row's Open to and `takes_swaps` against the post rules).

## Serial columns

`collection.serial_batches`, `serial_anchors` and `grid_fitted_at` are Drizzle-owned columns the worker writes (see `apps/worker/AGENTS.md`, Offline serials). `grid_fitted_at` (`20261108000000_add_grid_fitted_at`) is set while a collection's stored ranges come from a fitted grid and cleared when a rewrite no longer fits; the API's serial estimate reads it.

## Collection colours

Staff colour fixes live on the indexer's `collection` row: `text_color` and `background_color` hold the colour shown, and `source_text_color` / `source_background_color` (Drizzle-owned, `20261104150000_collection_colour_source`) hold the value a staff colour replaced, as the source gave it, null where the source applies. `collection_staff_colors` requires a staff-set colour to be lowercase `#` and six hex digits; a source stays unchecked, since 20 production rows hold malformed ones. `text_color_pinned` / `background_color_pinned` (`20261120120000_collection_colour_pins`) are nullable booleans: true keeps that staff colour over Cosmo's, null and false make it a fill the worker drops once Cosmo's colour equals it. They are nullable because the indexer's upsert writes NULL for a field it never sets, and `collection_staff_pins` allows a true pin only where its `source_*` is set. The history is the app's `mod_audit` (`collection_override` entries); no script puts it back on the rows after a resync (`apps/indexer/AGENTS.md`, Staff colours on `collection`). `.env.local`'s read-only indexer is what stops a local save from reaching production: it fails at the row lock and writes nothing, so keep `default_transaction_read_only=on` there.

## Cosmo sessions

`cosmo_session` is owned by `user_id` (cascade, but `anonymizeUser` deletes explicitly, since the user row is scrubbed, not deleted); `cosmo_address` is unique, so one Cosmo account has one row. `cookie_sealed` is AES-256-GCM under `COSMO_SESSION_KEY` with AAD `cosmo_session:<user_id>:<lowercased address>`, so a ciphertext copied to another row or owner fails to open; it is null once the session is dead, and a CHECK ties `dead_at IS NULL` to `cookie_sealed IS NOT NULL`. The sealed cookie never goes into `access_token`, whose readers take `findFirst()`, and no procedure returns it. Cleanup paths: disconnect, `anonymizeUser`, a new ban (`syncBan`), a reconnect of the same Cosmo account by anyone, and the worker deleting rows 30 days after `dead_at`. `last_used_at` is the last successful Cosmo answer to the session, written only by the worker; the keep-alive reads it with `created_at`. Every connect or renew clears `expiry_notified_at`, so the next 180-day cycle notifies again.

## Collection media

`collection_media` (one row per collection slug) is the source after an indexer rebuild: the worker's apply writes it back onto the rows. It has no session or user column, so the site records not which account shared a collection. `front_media` is Cosmo's URL and `front_media_copy` our bucket's, kept side by side; the indexer's `front_media` only ever receives the copy. `band_image_url` is recorded for later and never copied or shown. `has_voice` once true stays true, and `front_media_failed_at` times the last failed copy. Merge, apply and copy rules are in `apps/worker/AGENTS.md`.

## Cosmo objekt reads

`cosmo_objekt` and `cosmo_transferable` are keyed by token id, with no user, session, address or foreign key: what a connected account's session reported about a token. They sit in the app database, not the indexer's, so they survive an indexer rebuild (the stored reads write their corrections again) and need no indexer migration. `cosmo_objekt` holds Cosmo's latest read of each token and is the store of confirmed serials (`serial_eligible`, loaded by `cosmo_objekt_confirmed_idx`); `cosmo_transferable` holds the confirmed `transferable` value. The `serial_due` and `transferable_due` flags and their partial indexes make "what is new" one index scan on tables that reach millions of rows. Both tables are kept for good: no job deletes a row and no account event touches one. Rules are in `apps/worker/AGENTS.md`, Cosmo objekt data.

## Link history

`address_link_event` is append-only and has no foreign key on `user_id` or `actor_id`: an event outlives its account. `user_address` stays the authority for the current holder. The backfill has two gaps: links made between its migration and the deploy, and past holders who never traded (only trade snapshots name them). `holdersOf` adds the current holder to cover the first.

## Indexer data

- `transfer` is the complete ownership history. A mint has `from` = the null address; a spin has `to` = the spin address.
- Ownership of address X at time T: `DISTINCT ON (objekt_id) … WHERE timestamp <= T AND (from = X OR to = X) ORDER BY objekt_id, timestamp DESC`, then keep the rows where `to = X`. Mints and spins need no special case.
- Production `transfer` also holds legacy Polygon-era rows from before Cosmo moved to Abstract, so it outnumbers any Abstract-only resync. Scope local-versus-production diffs to the Abstract era.
- `indexer` is `drizzle-orm/node-postgres`, so `indexer.execute(sql…)` returns `{ rows }`. Use it for Postgres-only SQL such as `DISTINCT ON`.
