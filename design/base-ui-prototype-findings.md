# Base UI (cnippet) prototype — findings

Date: 2026-09-20. Prototype lives in `apps/lab` (Vite + React 19 + Tailwind v4 + TanStack Router, code-based routes). Throwaway; delete when the migration lands.

Question asked: can `apps/website` move from intentui / react-aria-components (RAC) to Base UI via the cnippet registry without losing behaviour?

## Verdict

**Go, with two known gaps.** Every hard interaction in the app has a Base UI equivalent that is equal or simpler than the RAC version. SSR under TanStack Start is clean. The two gaps are the colour picker (used by the objekt colour filter) and the date field (used by the snapshot picker); both have workable fallbacks.

## Gaps vs react-aria

1. **ColorPicker** (`filters/filter-color.tsx`: ColorArea + hue slider + hex field + EyeDropper in a Popover). Base UI and cnippet have nothing. Native `<input type=color>` opens the OS picker, cannot be embedded in a popover, no eyedropper on Safari. Options: keep `@react-stately/color` with a hand-built UI, or `react-colorful` (~3 kB). Decision needed before the filter bar rewrite.
2. **DateField / DatePicker** (snapshot picker). cnippet ships `Calendar` (react-day-picker) but no segmented field. Fallback used: native `<input type=date>` + Calendar in a Popover, both bound to one state. Loses per-segment keyboard editing. Acceptable for the snapshot use case.
3. **Searchable multi-select.** Website's member / class filters compose `Select > Popover > Autocomplete > ListBox`. Base UI would use `Combobox multiple`, which changes the trigger into an input with chips. Design choice, not a blocker.
4. **Nullable values.** Base UI `Select.onValueChange` and `NumberField.onValueChange` are `T \| null`; every handler needs a guard. RAC `Key` selection never nulls.
5. **Toolbar-style Select trigger.** cnippet `SelectTrigger` is a full-width form field; the filter bar uses raw `Select.Trigger` + `buttonVariants`. Worth a small local wrapper.

## Token mapping trap

shadcn / cnippet `--*-foreground` means **text on a tinted 8–16 % chip**. intentui `--*-fg` means **text on a solid fill**. Website's `app.css` aliases `--color-success-foreground: var(--success-fg)`, which makes cnippet's `Badge variant="success"` render dark green on dark. Correct alias is the intentui `*-subtle-fg` token (fixed in lab `app.css` for success / warning / info). Apply the same when migrating website.

## Unrelated bug found on the way

`cqi` inside `writing-mode: vertical-rl` text (the card stripe) resolves against the *vertical* axis; with `container-type: inline-size` that axis is not contained, so Chrome falls back to viewport units and the stripe text rendered at ~60 px. Use `cqw` for anything inside rotated text. Fixed in lab `objekt-card.tsx` and the mockup. Check `apps/website` `--radius-photocard: 5.4cqi` and the stripe styles in `objekt-view.tsx` for the same pattern.

## Recommended migration order (website)

1. Add cnippet components into `src/components/ui/`, fix the token aliases above, add `base-ui` chunk group. Keep `intentui/` alive alongside.
2. Swap by primitive frequency: button + link (47 imports) → field / input / text-field / textarea (36) → modal / sheet (20) → menu / popover / select (21) → tabs → checkbox / switch / radio → rest.
3. Do the filter-bar redesign (mockup) together with the 32 files that import `react-aria-components` directly; that folder is the last RAC user.
4. Decide colour picker (gap 1) before step 3.
5. Remove `react-aria-components`, `tailwindcss-react-aria-components`, `@react-aria/optimize-locales-plugin`, `@plugin` line in `app.css`, `intentui/`.

## virtua inside a Base UI Drawer (round 8)

- Use `Virtualizer` + `scrollRef` pointing at the drawer's `[data-slot=scroll-area-viewport]`, not `VList` (nested scroller eats wheel) or `WindowVirtualizer` (measures the window).
- `startMargin` is not auto-measured when `scrollRef` is passed: compute `grid.top − viewport.top + viewport.scrollTop`, round it, re-measure with a ResizeObserver on viewport and content.
- Grab the grid with a callback ref; it mounts after data resolves, a `useRef` + mount effect reads null.
- Never set `viewport.scrollTop` yourself; use `handle.scrollToIndex(row, { align: "start", offset: -stickyHeight })` inside `requestAnimationFrame` on mount.
- Uniform row chunks + explicit `itemSize` skip the measurement pass. Website already has `virtua@^0.51.3`.
- Layout: content container `max-w-(--breakpoint-2xl)` on main and nav (matches website); banner's blurred copy uses `left-1/2 w-screen -translate-x-1/2` to escape the container.

## Round 9

- **`w-screen` full-bleed layers cause horizontal scroll.** The banner's blurred copy uses `left-1/2 w-screen -translate-x-1/2` to escape the content box. `100vw` includes the classic scrollbar gutter, so on any page with a vertical scrollbar the layer is ~11 px wider than the viewport and the document scrolls sideways. Fixed at the root layout wrapper with `overflow-x-clip`, not `overflow-x-hidden`: `clip` does not create a scroll container, so the sticky nav keeps working. `apps/website` has the same `w-screen` banner layer — apply the same wrapper there.
- **Base UI `Menu.CheckboxItem` already keeps the popup open** across picks; no `closeOnClick={false}` needed. Drive it with controlled `checked` + `onCheckedChange`, and a handler that refuses the change (e.g. "never deselect the last artist") simply re-renders it checked — no extra guard in the item.
- **Base UI menus do not open from a synthetic `element.click()`** in a test harness; they listen for pointer events. Dispatch `pointerdown / mousedown / pointerup / mouseup / click` (or drive a real click through the devtools protocol) when scripting them.

## Round 10

- **A remount-blind `useElementSize` breaks the banner's blurred backdrop.** `ProfileBanner` returns `null` when the banner is hidden, so the measured node is destroyed and a brand new one mounts when it is shown again. A hook built as `useRef` + a mount-only `useLayoutEffect` keeps observing the *detached* node: Chrome reports it as 0×0 and never fires again, so the full-bleed blurred copy gets `height: 0` and the banner renders clamped to the content box with bare edges. Fix is in the hook, not the caller — hold the node in state and set it through a callback ref, so the `ResizeObserver` re-attaches on every swap. `apps/website` has the same shape (`@custom-react-hooks/use-element-size` + a conditional `ProfileBanner`); check it there when migrating.
- **`Menu.SubmenuTrigger` already appends its own `ms-auto` chevron**, so a second `ml-auto` child (stacked artist avatars) right-aligns next to the chevron rather than fighting it — the first auto margin eats the free space, the second gets none.
- **A Base UI Sheet does not know about the router.** A `Sheet` holding TanStack `Link`s stays open after navigation; set `open` to false in each link's `onClick`.

## Round 11

- **A trigger-driven `Combobox` needs `initialFocus`.** The select-shaped combobox (a `Combobox.Trigger` button, with `Combobox.Input` *inside* the popup) opens and then closes itself again on the next tick: nothing in the popup takes focus, so Base UI treats it as a focus-out. Pass `initialFocus={inputRef}` on `Combobox.Popup` — that fixes both the phantom close and the "opening it focuses the search field" requirement in one prop.
- **cnippet's `ComboboxPopup` anchors to the chips, not the trigger.** It reads `chipsRef` out of its own context and uses it as the positioner anchor, which is null in a trigger-driven shape. Pass `anchor={triggerRef}` explicitly.
- **`Combobox.List`'s render-function child must be the list's only child.** `ComboboxListProps.children` is `ReactNode | ((item, index) => ReactNode)`; add a second child (e.g. `Combobox.Empty`) and TS collapses the union to `ReactNode[]` and rejects the function with `TS2322: Type '(x: T) => Element' is not assignable to type 'ReactNode'`. `Combobox.Empty` belongs next to the list inside the popup anyway.
- **cnippet `ComboboxItem` (and `SelectItem`) hardcode a two-column grid**, `grid-cols-[1rem_1fr]`, with the `ItemIndicator` pinned to column 1 and the children wrapped in a plain `div` in column 2. The check column is reserved whether or not the combobox is multi-select, and any row layout of your own has to start inside that second column — the item itself is not the flex container it looks like.
- **cnippet's `SelectGroupLabel` cannot be restyled.** It spreads `{...props}` *after* its own hardcoded `className`, so a passed class replaces the base styles instead of merging. Every other cnippet part destructures `className` and runs it through `cn()`; fixed the same way in the lab (needed to make the artist group label sticky).
- **Base UI multi-select `Combobox` keeps the popup open across picks and clears the filter query** on each pick, so the list springs back to the full set after every Enter. Base UI's own `Select` with `multiple` does not reset anything, which is why the two facets feel different even though both are multi-select.

## Round 12

- **`cqi`-based radii need a container context on *every* face of a 3D flip.** `--radius-photocard: 5.4cqi` resolves against the nearest `container-type: inline-size` ancestor. `ObjektCard` carries its own `@container`, so the flip's front face is fine, but a hand-built back face sits outside it and `cqi` falls back to the viewport — the back rendered as an oval. Put `@container` on the flip's outermost (untransformed) wrapper, never on the `transform-3d` element itself: `container-type` implies layout containment, which makes the browser drop `transform-style: preserve-3d`.
- **A Base UI `Menu.Item` cannot own a `Dialog.Trigger`.** Clicking the item closes the menu, and the popup unmounts with it — taking the nested `Dialog.Root` and its open state along. Either hoist `Dialog.Root` above `Menu.Root`, or (what the lab does, matching `AddToListDialog`) make the dialog controlled and render it as a sibling of the menu. A dialog that is opened from both a menu item and a plain page button is simplest as controlled-only.

## Round 13

- **cnippet `Input`'s `className` lands on the bordered wrapper, not the `<input>`.** The component renders `<span data-slot=input-control class={cn(base, className)}><InputPrimitive class={sizePadding}/></span>`, and the inner input keeps its own horizontal padding (9 px at `size="sm"`). A `pl-8!` meant to clear an absolutely positioned search icon therefore stacks on top of that 9 px: the placeholder started 42 px in against an icon ending at 26 px, a 16 px gap next to a 10 px border-to-icon inset — the "search icon gap" the filter bar had. Budget the inner padding: `pl-6!` (24 + 1 px border + 9 px) puts the text at 34 px, i.e. the same 8 px the nav-search trigger gets from `gap-2`. `apps/website` uses intentui `SearchField`, so check where its padding class lands before porting the number.
- **cnippet's danger token has the same `*-foreground` trap as success / warning / info.** `--color-destructive-foreground` aliased `--danger-fg` (white, text on a solid fill), so `Badge variant="error"`, `data-[variant=destructive]` menu items and every `text-destructive-foreground` label rendered white on a plain or 8 %-tinted background. Correct alias is `--danger-subtle-fg`; fixed in lab `app.css` next to the other three.
- **A Base UI `Popover` opened from inside a `Sheet` needs no z-index work.** Both popups sit at `z-50`, and the popover's portal mounts after the sheet's, so DOM order alone puts it on top. Dismissing the popover leaves the sheet open.

## Round 14

- **cnippet's `SelectTrigger` carries an intrinsic `min-w-36`.** `selectTriggerVariants`' base class is `… w-full min-w-36 …`, and `SelectTrigger` spreads it straight through, so the trigger can never shrink below 144 px however narrow its column is. `SelectButton`, in the same file, already neutralises it with a trailing `min-w-0` — `SelectTrigger` does not. That is the whole "Currency select overflows the Create list dialog" bug: a `w-28` (112 px) `flex-none` column holding a `min-w-36` trigger renders 32 px wider than its own box and runs past the dialog's edge, and `min-w-0` on the *column* does nothing because the overflow comes from the trigger's own minimum. Two fixes, both needed: drop `min-w-36` from the cva base (done in the lab), and size such a row with `grid-cols-[minmax(0,1fr)_minmax(0,6.5rem)]` rather than flex `w-28`, since a bare `1fr`/`auto` track is also sized by the trigger's intrinsic width. `profile-toolbar.tsx` had already been working around it with `className="w-auto min-w-0"`, which is the tell.
- **A Base UI Sheet unmounts its popup when it closes**, so anything that inspects what the sheet *renders* only sees it while the sheet is open. The lab's dev-only facet-parity guard (desktop facet keys must equal mobile facet keys) therefore registers the mobile key list from `FilterSheet` itself — always mounted, only CSS-hidden above `md` — instead of from the `FacetControls` inside the popup, which would otherwise read as "mobile renders no facets" every time the sheet is shut. Parent effects run after child effects, so the comparison can sit in a plain `useEffect` with no dep array in the toolbar component.
- **`display: contents` does not survive a `max-md:hidden` sibling variant.** Wrapping a fragment of toolbar children in `<div className="contents max-md:hidden">` to hide them as a group puts two display utilities of equal specificity in the same layer, and which one wins depends on Tailwind's emitted order rather than on the variant. Pass the responsive class down to each control instead (the lab's `FacetControls` takes a `controlClassName`).

## Round 15

- **cnippet's `PopoverPopup` pads its viewport, not the popup**, so a caller's own `p-*` stacks on top of it. `Popover.Viewport` carries `px-(--viewport-inline-padding) py-3 [--viewport-inline-padding:--spacing(3)]`, while `className` on `PopoverPopup` lands on `Popover.Popup`, one level out — a `<PopoverPopup className="p-3">` therefore renders ~24 px of inset, not 12. It is the same shape as the round-13 `Input` trap (the class lands on the wrapper, the inner element keeps its own padding), and the fix belongs in the component: a `padding` prop (`"default" | "none" | "sm"`) that swaps the viewport's padding utilities, with callers dropping their `p-*`. Note that `Viewport` also carries `has-data-[slot=calendar]:p-2`, a `has-` variant with higher specificity, so a popup containing a `Calendar` keeps the 8 px calendar inset whatever `padding` says.
- **Base UI's `Select.Value` render-function child replaces the placeholder.** `<SelectValue placeholder="…">` only renders while the value is null, and passing a function child takes that branch over, so the function must handle `null` itself. `data-placeholder` is still set on the element, so the muted styling keeps working.
- **chrome-devtools `take_snapshot` uids go stale across a React re-render**, not just across navigation: a card in a grid that re-renders (hover, image load) invalidates the uid and `click` fails with "no longer exists". Driving the page from `evaluate_script` is steadier — a plain `element.click()` is enough for React `onClick` handlers and for Base UI `Tabs`, while menus, popovers and `Select` still need the dispatched `pointerdown / mousedown / pointerup / mouseup / click` sequence from round 9.

## Round 16

- **cnippet's right-hand `Drawer` is `w-[calc(100%-48px)]`, and that gutter is not optional.** `DrawerPopup` hardcodes the width per position, so a `max-w-*` class cannot widen it — on a 390px phone the popup is 342px, and the drawer's header grid (`minmax(0,11rem)_1fr`, where the `1fr` column also holds a "View in Apollo" button and a `dl` whose labels alone are ~84px) needs ~374px. The result is not a popup wider than the viewport, it is the popup's `ScrollArea` viewport scrolling sideways, which reads as "the drawer is shifted left and the card is cut". `max-sm:w-full` on `DrawerPopup` overrides it cleanly (the class lands on `Drawer.Popup` itself, unlike the round-13/15 wrapper traps).
- **A `DrawerPopup`'s own `scrollWidth` is useless as an overflow signal.** cnippet paints a 48px `::after` bleed past the popup's outer edge (`after:inset-s-full after:w-(--bleed)`, so the swipe never reveals the page behind it). A pseudo-element contributes to `scrollWidth` but appears in no element walk, so `popup.scrollWidth > popup.clientWidth` is permanently true by 48px. Measure the popup's *children* against its own right edge instead.
- **`TabsList` with `w-full` inside an `overflow-x-auto` strip clips the underline rule, not the tabs.** `w-full` pins the list to the scroller's width while the `shrink-0` tabs spill past it, so the strip does scroll but `border-b` and the Base UI indicator both stop at the container edge — which is what "the strip is clipped instead of scrolling" looks like. `w-max min-w-full` sizes the list to its tabs and still fills a wide viewport.
- **A dev-only overflow guard has to be told what clipping is deliberate.** `src/lib/dev-overflow-guard.ts` walks `[data-overflow-guard]` (the `<main>`, since the round-9 `overflow-x-clip` wrapper hides page overflow from `documentElement.scrollWidth`) plus every open drawer / sheet / dialog popup, and stops descending at anything that clips. Four things clip on purpose and must be skipped or every page reports a hit: form controls (`<input>` scrolls its own value), `text-overflow: ellipsis` (`truncate`), `sr-only` 1×1 boxes, and declared scrollers — the lab marks those `data-scroll-x`. It found one bug nobody had reported: the Progress rows' `grid-cols-[6.5rem_1fr_7rem_4rem]` needs 350px of fixed tracks and gaps against 348px of content box.
- **Overlays portal into `<body>`, so a route-change effect never sees them.** The guard re-checks from a `MutationObserver` on `<body>`, 700ms after a popup mounts — cnippet's drawer transition is 450ms, and measuring mid-transition reports the popup's transform offset as a 2px overflow.

## Round 17

- **Base UI's `Switch` puts your `id` on its hidden `<input>`, not on the `role=switch` element.** `Switch.Root` renders a visible `<span role=switch>` (with a generated id like `base-ui-_r_2s_`) plus a visually hidden `<input type=checkbox aria-hidden>` for form participation, and the `id` you pass lands on the *input*. Two consequences. First, `document.getElementById(id)` in a test or a guard hands you the hidden input, whose `aria-checked` is null and whose `data-checked` never appears — the visible element carries both, so a state assertion against the id silently reads the wrong node. Second, the visible element is given `aria-labelledby="${id}-label"`, so a `<label htmlFor={id}>` that does not *also* carry `id={`${id}-label`}` leaves that reference dangling and the switch has no accessible name by spec (Chrome happens to recover one from the wrapping label, which is what makes it easy to miss). Set both on the label.
- **A `grid-template-rows: 0fr → 1fr` disclosure has to keep its content mounted, and the mount flag belongs to whoever can open the row.** Unmounting on close leaves the collapse nothing to animate; but holding "has been open once" in the row's own `useState` breaks the moment a *second* control opens it — the lab's "Closest to complete" panel sets the parent's open list, the row expanded to a 929px-tall empty box because its private flag was still false. Keep both the open set and the mounted set in the parent. The mounted content then survives the collapse, so the closed row also needs `inert` — a `0fr` track still holds focusable cards in the tab order and the a11y tree.

## Round 19

- **A chip row that lives inside one page's filter bar is a reset that only some pages have.** `FilterBar` owned the active-filter chips + "Clear all" inline, so Home / Market / List detail had a reset and the two profile tabs — which render `ProfileToolbar` against the *same* store — had none, while Activity had a hand-copied row of its own. Extracted to `src/components/filters/active-chips.tsx`, generic over the chip type (`{ key, label }` plus whatever `remove` payload the caller needs), and rendered by `FilterBar`, `ProfileToolbar` and Activity. The chip's `key` is the styling contract: `member:<name>` gets the member dot, `collectionNo:<no>` gets the mono treatment, so every surface that builds chips keys them the same way and gets the same row for free.
- **Local UI state next to a shared store needs the reset widened, not duplicated.** Progress's Show group (All / Owned / Missing) is `useState` in `ProgressView`, so the store's `reset` cannot clear it. `ProfileToolbar` takes an optional `onReset` that overrides `f.reset` for *both* the chip row and the mobile Filters sheet; Progress passes `() => { filters.reset(); setShow("all") }`. Splitting it (chips reset the store, sheet resets everything) is how the two drift.
- **A page-local facet control that writes a shared store field is a duplicate, not a shortcut.** Round 17's Show row carried its own Season `MultiSelect` bound to `filters.season` — the same field the toolbar's Season facet writes — so the Progress tab rendered two Season dropdowns that mirrored each other. Only page-local state (Show) belongs outside the shared `FACETS` table; anything in the store is already on screen.
- **Accent colour on a value label reads as a state the row does not have.** The 100% rows' `6 /6 (100.0%)` was `text-accent-solid`, which made completion look like selection. The label is now identical on complete and incomplete rows (`text-fg` count, `text-muted-fg` remainder) and the only completion cue is the check glyph inside the member dot.

## Round 20

- **The real Cosmo member colours are one unauthenticated POST away, and the lab had no gray members by choice — it had them by omission.** Two hand-copied maps (`filters/member-colors.ts` and a second copy inside `profile/profile-data.ts`) covered 16 members between them, so 34 of the 50 in `fixtures/collections.json` fell back to `#8a8f9c` / `#999` — every idntt member but three, HeeJin, and most of tripleS. `primaryColorHex` lives on `CosmoMemberBFF`, and while the Cosmo API itself needs a token, the deployed app re-serves it through oRPC: `curl -X POST https://objekt.top/rpc/config/getArtists -H 'content-type: application/json' -d '{}'` returns all three artists with `artistMembers[].primaryColorHex` and no auth. All 50 colours in the consolidated map are real Cosmo values; none are curated. (`/api/artists` and friends 404 — the proxy target only serves the collection / objekt endpoints; the oRPC route is `/rpc/<router>/<procedure>`, POST only, 405 on GET.)
- **A colour map keyed only by member name cannot answer for a row that has no member.** Four collection rows carry a unit or an event there (`idntt`, `id6 X id11`, `itsnotover`, `TokyoHaus`), and the caller that needs the colour most — the active-filter chip row, which only knows `member:<name>` — has no artist to hand. Deriving `member → artist` from the fixture inside `member-colors.ts` keeps `memberColor(name)` one argument at every call site and means a refreshed `collections.json` cannot reintroduce a colourless row. The last-resort value is `currentColor`, not a grey: it inherits the chip's own text colour, so an unknown name reads as neutral rather than as a member whose colour is missing. (It was written as "the colour the 'All' chip already uses"; round 34 removed that chip and the fallback is unchanged, because `currentColor` never named the chip, only its ink.)
- **Brand colours are swatch colours, and several have no edge of their own.** YuBin is `#FFE3E2`, SeoAh `#CFF3FF`, JiWoo `#FFF800` — on a light surface those dots disappear entirely and on the dark one they bloom. Every render site (member chips, active chips, both Progress dots) now pairs the swatch with `ring-1 ring-fg/15`, which costs nothing on a saturated colour and is the only thing holding the pale ones. The Progress dot's completion check already had the matching problem solved a different way (`mix-blend-difference` rather than a fixed white); the two go together. Nothing colours *text* with these.
