# Design

## Context

- `createOffer` (`packages/api/src/services/offer/index.ts`) checks You get against the partner's lists on Trade (`allowedEntries`, `matchEntry`, `refusedCollectionAsks`). It checks You give only for ownership and reservation (`checkItems`). `givesWanted` already looks up the partner's want lists, but only to decide `firstListed`, never to refuse.
- `counteredGives(conversationId, me)` returns the gives of the open offer being countered (the partner's gives). The asks of that offer, which become the counterer's gives, aren't read anywhere yet.
- The You give picker (`picker/mine.ts`) narrows by `wantSlugsOf(partnerId, true)` (discoverable want lists) when `matchOnly` is set.
- Offers are read through one SQL in `services/offer/view.ts`, and `itemViews(row, viewerId, …)` shapes each item for one viewer. Chat cards, live events and the offer page all use it.
- `offer_item.list_id` already records which list each ask matched through. The offer itself doesn't record which post it started from, but the builder knows it: `post` in `offerSearchSchema`.
- Per-user switches follow `showOnline`: a `user` column (`auth-schema.ts`), a Better Auth `additionalFields` entry (`services/account/auth.ts`), an optional field on `user.update` (`schemas/user.ts`, `services/account/user.ts`), and a switch in `features/account/sections/general.tsx`.

## Goals / Non-Goals

**Goals:** a server-side gate on the give side, decided by the recipient; labels computed per viewer in the existing offer read; no new procedure.

**Non-Goals:** caching the labels; backfilling `post_list_id` for old offers (they read as "not from a post"); touching `firstListed`.

## Decisions

1. **Gate on the post's own want list.** On 2026-11-10 the user chose per post: an offer on a have or sale post paired with a want list may give only from that list (`postWantedAmong`, through the post's `linked_list_id`); a post without one, or with an empty or hidden one, takes anything; an offer on no post gives from any discoverable want list (`wantedAmong`), as the first version did for every offer. The post is the one the asks came through, else the client's `post` for a gives-only offer, which the server stores as no post. Automatic per post for everyone was rejected: on production, 61% of first offers on paired posts (3,562 since 2026-10-25) gave something off that post's want list, and 792 of them were accepted. The builder learns each post's want list from `PartnerList.want` and keeps the picker to it through `wantList`, so the locked switch and the server read the same list.
2. **Labels use all of the recipient's want lists.** Only the recipient sees the labels, and an objekt on their private want list is still something they want. The gate and the labels may differ on that one point, and that's intended.
3. **No want list on Trade (or only empty ones) means no filter on an offer with no post.** Refusing every give to a user with the switch on and no want list would quietly turn them into cash-only. The switch description says so, so the user isn't surprised. The rejected alternative was refusing the give, or greying out the switch until a want list exists. Greying out hides the setting behind a step the user may not connect to it.
4. **Counter exemption through the countered offer's asks.** Add `counteredAsks(conversationId, me)` beside `counteredGives` in `picker/shared.ts`, or widen it to return both sides in one query. It returns the objekt ids and any-copy slugs the open offer to `me` asked from `me`. A give whose objekt id, or whose collection when the ask was any copy, is in that set is exempt. The view uses the same rule through `o.parent_id`, so the label doesn't flag what the recipient asked for.
5. **Store the post as `offer.post_list_id`.** `createOfferInputSchema` gains an optional `post` (list slug, max 12). The builder sends the Offer on choice (decision 13), and nothing for No post. `createOffer` resolves it to one of the partner's lists in `askableOnTrade` (bound have or sale, discoverable). Anything else, such as a WTB post's want list, a slug that isn't theirs, or a list taken down meanwhile, stores null and never refuses. Old tabs send no `post` and keep working. The rejected alternative was deriving the post from the conversation's newest post card: an offer page opened from a Trade row isn't always tied to a card, and the card can be newer than the offer.
6. **Labels come from the offer read, not the client.** `view.ts` selects `o.post_list_id` and the post's slug and name. For each item it selects `wanted` (an `EXISTS` on `list_entries` ⨝ `lists` where `user_id = o.to_user_id AND list_type = 'want'`) and `asked` (the item matches an ask of `o.parent_id`). The offer's `post` (slug and name) goes to both people. `itemViews` sets `notWanted` only when `viewerId === row.to_user_id`, so the sender's payload never carries it. There is no "From another post" label: a recipient who wants one post per offer gets it enforced (decision 10), and one who allows asks across posts has said they don't mind. `fetchOffers(ids, reader)` runs the per-item `EXISTS` only for offers sent to the reader, since nobody else sees the result (measured in Risks).
7. **Builder learns the rules from the candidates pages.** Every `candidates` response carries `partnerRules` (`wantedOnly`, `asksClosed`), each true only where the rule would filter; the builder reads it from the theirs page it already loads. That saves a round trip, since the builder already loads this page. The rejected alternative was a separate `offer.partnerRules` procedure.
8. **Refusal `not_wanted`** joins `OFFER_REFUSALS` with `{ objektIds }`, the same shape `not_listed` uses. The web maps it in `features/offers/refusal.ts` to "Not on their wants" through the existing per-pick refusal path. Strings go in `en`, `ko` and `ja`, worded in ko 합니다체 and ja with full-width punctuation.
9. **The two switches sit in General.** `/account/trade` exists only in the unapplied `trade-active-hours` change. Whichever change lands second moves or keeps the switches. Only the web section changes; the columns and API stay.
10. **One post per offer is the recipient's choice, on by default for asks across posts.** First the user made it a rule for everyone, then on 2026-11-11, seeing that 80 of 311 senders (26%) and 52 recipients had offers across posts in 17 days (246 offers, 58 accepted), added "Let people ask from more than one post", on by default (`user.multi_post_asks`). With it on, `createOffer` skips the refusal and stores no post for an offer across posts; `partnerRules.onePost` is false, so the builder keeps its List choice and shows "Offer on {post}" only when it started from a post, and `suggestOffer` doesn't narrow row matches. Earlier: On 2026-11-10 the user turned "Only asks from one post" into a rule for every recipient with a have or sale list on Trade: 3.3% of first offers ask across two posts, accepted a little less often (24.7% against 30.7%). `post` comes from the client, so the rule doesn't depend on it: every non-kept ask must match through one and the same `askableOnTrade` list, and when `post` resolves to one of them, that one. The rejected alternatives were a per-recipient switch (the first version of this change, applied locally only) and an inverse switch to take asks across posts.
11. **Choosing the list.** Today `matchEntry` takes the first entry that fits, and an objekt may sit on two lists. The target list is the resolved `post` if there is one. Otherwise it's the `listSlug` the first get item carries (the picker sends it), and otherwise the first list on which every ask has an entry. Each item then has to match an entry on that list, and `offer_item.list_id` records it. Put this in a pure function next to 3.1's (`lib/offer-wanted.ts` or a sibling `offer-one-post.ts`) with tests for the spec's scenarios, including an objekt on two posts.
12. **Refusal `other_post`** carries `{ objektIds, collectionSlugs }`, the same shape as `not_listed` for any-copy asks. The web maps it to "Not on {list}", using the builder's chosen list name.
13. **The builder chooses the post up front.** When the theirs page is over lists with at least one list, the header holds Offer on: the partner's lists and No post. It opens on `start`, else the matches' post (`match=post`, or the slug `suggestOffer` returned), else `to` when it is one of those lists (a row's lead post), else the first get pick's list, else the first list. You get's picker is fixed to it, with no List choice. A get pick on another list reads "Not on {post}", and any get pick under No post reads "No post chosen". The rejected alternative was keeping List in the picker and binding the post to it, which hid the post the offer is on behind a picker control.
14. **Collection asks become opt-in.** `createOffer` already branches on `hasLists` (`partnerHasLists`). When it's false, it now also reads `allow_collection_asks`: with that off, any non-kept get item is refused `not_listed` (old tabs already know this code), and `collectionAddrs` is never read. `offerCandidates` for `theirs` returns no items and a new `asksClosed: true`, and the builder shows the line instead of the Add button. Kept items in a counter stay askable, since the recipient offered them. Reusing `not_listed` rather than adding a code keeps tabs from before the deploy showing the right words.
15. **The nudge is a toast off the decline success, gated by the server.** The offer view carries `suggestWantedOnly`, only for the recipient: true while their `only_wanted_offers` is off, they have a discoverable want list, and an item is `notWanted`. `useOfferActions` (`features/offers/actions.ts`) reads it from the declined offer and, on success, adds a `toastManager` toast with a Turn on action that calls `user.setOfferRules({ onlyWantedOffers: true })` (a small procedure beside `user.updateAccount`, whose input also needs the name and the picture flags) and refreshes the session. It's marked as shown in the existing `useNoticesStore` (as `link/privacy-removed-notice.tsx` does) the moment it shows, so it's per browser: a toast's `onClose` fires on its timeout as on a dismissal, so a closed toast can't count as Not now. The alternative was a stored per-account dismissal column, rejected because a migration for a hint costs more than the hint is worth, and showing it again on another device is harmless. A toast fits better than an inline banner, since the declined offer card moves to its closed state and has no room for one.
16. **Row matches pick one post on the server.** `suggestOffer` (`services/offer/picker/index.ts`) already has a post mode (`post`) for "Matches of one post". For a partner who takes asks from one post, when no `post` is given, the result isn't a Can swap pair and You get would be filled, it counts the get matches per partner list. It then reruns as post mode on the list with the most, breaking a tie by the row's lead post, and returns that list's slug so the line and Offer on name it. Cut to one post, You get may hold fewer matches than You give, so the two sides are compared again and the bigger one fills. A Can swap pair returns its own post's slug. Doing it in the service keeps the builder unaware of the rule, and the 50-a-side cap still applies to one list. The rejected alternative was filtering on the client after the matches arrive: the cap would then cut before the filter, and a 50-row page could hold fewer from the chosen post than it has.
17. **Counter exemption for one post per offer** reuses `counteredGives` (the `kept` set the get check already reads) and is keyed on objekt id. A kept objekt that is also listed gets a `list_id` from `matchEntry`, so `list_id IS NULL` can't mark it.
18. **The Messages notice** is one inline notice at the top of the Inbox (the shape of `link/privacy-removed-notice.tsx`), dismissed through `useNoticesStore`, so it's per browser. It shows when `user.only_wanted_offers` is false and the user has a discoverable want list. Every account starts with the setting off (the user chose one default for all accounts on 2026-11-10), so the notice is how most people find it. Turn on calls `user.setOfferRules({ onlyWantedOffers: true })`, the same call the nudge makes.

## Risks / Trade-offs

- [A sender's builder opened before the recipient turns the switch on] → the server refuses `not_wanted` on send and the pick is marked. That's the same path as a pick that went unlisted.
- [Pre-deploy tabs don't know `not_wanted`] → the English `message` from `refuseOffer` shows as the generic refusal. That's acceptable for one deploy.
- [Label drift: wants change after an offer is sent, so a label can appear or disappear] → the label reads "your wants" as they are now, which is what the recipient decides on. The spec doesn't promise a snapshot.
- [One post per offer stops a sender from asking across two posts in one offer, even when the recipient would take both] → 3.3% of first offers today. The sender sends a second offer once the first closes (one open offer per conversation), and the builder's line says so. Recheck the `other_post` refusals two weeks after release.
- [Collection asks off by default refuse about 13% of first offers, some of them good trades (41.7% were accepted)] → the sender sees why in the builder and can still Message or offer gives and a top-up, and the recipient's switch description says how to open it again. Recheck the refusal count two weeks after release.
- [Receivers turn the switch on and get fewer offers] → it's opt-in and off by default, and the description says what it does.
- [Per-item `EXISTS` in the hot chat read] → measured on production (read-only, 2026-11-11) for the heaviest want-list owner (30,485 entries) and the most listed collection: about 1.2 ms per give through `lists_user_id_idx` and a bitmap AND on `list_entries`, so at most about 60 ms for a full side. No new index. If it grows, fold it into one lateral `array_agg` of the recipient's want slugs per offer.
- [`offer_post_list_idx` is built without `CONCURRENTLY`] → Drizzle runs each migration in a transaction, where `CONCURRENTLY` can't run, and `offer` held 6,951 rows (3 MB) on 2026-11-11, so the lock lasts milliseconds.

## Migration Plan

`20261110121908_offer_rules` adds `user.only_wanted_offers`, `user.one_post_offers` and `user.allow_collection_asks` (all `boolean NOT NULL DEFAULT false`) and `offer.post_list_id integer REFERENCES lists(id) ON DELETE SET NULL`; `20261110131530_offer_post_list_idx` adds the partial index on `post_list_id IS NOT NULL`; a third drops `user.one_post_offers` (`IF EXISTS`), since the switch became a rule after the first migration ran locally, and past migrations are never edited. No release reads that column, so adding and dropping it before the deploy is safe. Applying the migration needs the user's approval. To roll back, deploy the previous image; the columns are ignored.
